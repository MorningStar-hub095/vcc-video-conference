# Q3 冒烟脏数据 —— 方案建议与落地设计

> 面向 `deploy/verify.py` 每次运行都向 `t_user` 插入一条 `smoke_*` 用户且从不清理的问题。
> 本文只做分析设计与方案建议，**尚未修改任何代码**。

## 二、建议结论：选「冒烟环境隔离」，但要选对实现方式

我推荐 **方案 A（环境隔离）**，不推荐「跑完直连 MySQL 删数据」。

### 杀手锏理由：`tel` 前缀清理条件会误删真实用户

verifier 生成的号码是 `139%08d`（`verify.py:112`）。若采用直连清理，最自然的写法必然是：

```sql
DELETE FROM t_user WHERE tel LIKE '139%';   -- ✗ 危险
```

**139 是中国移动号段**，真实用户完全可能命中。这在开发期看不出来，一旦库里有真实数据就是删库级事故。

相对安全的条件是 `name LIKE 'smoke\_%'`，但它依赖 verifier 的命名约定——哪天有人改了 `name` 的生成规则，清理条件就静默失效（漏删），或者反过来误伤。

### 其余理由

| 维度 | A 环境隔离 | B 直连清理 |
|---|---|---|
| 误删风险 | 0（碰不到生产卷） | 中～高，取决于 WHERE 条件 |
| 能否验证 `schema.sql` 完整性 | ✅ 每次都是空库全新初始化 | ❌ 永远测不到"首次部署"路径 |
| 阶段 1 的负向用例能否落地 | ✅ 可任意造脏数据 | ❌ 重复注册/错误密码/超长字段会灌进生产库 |
| 可重复性与 CI 适配 | ✅ 幂等，天然适配流水线 | ❌ 跑 N 次留下 N 条痕迹，自增 ID 持续漂移 |
| 生产环境可否直接跑 | ✅ 零副作用 | ⚠️ 需给冒烟脚本生产库写权限 |
| 改动量 | 新增 2 个文件，**零改动现有文件** | 改 `verify.py` |
| 单次耗时 | MySQL 初始化约 20–40s | 0 |

> 第 3 条是决定性因素：阶段 1 计划补**负向/边界用例**（重复注册、错误口令、空包、超长字段）。这类用例本身就要大量制造非法数据，放在共享库里跑等于一边测试一边污染。

## 三、落地设计（关键：用 overlay，不是复制一套 compose）

### 3.1 为什么是 overlay 而不是复制 `docker-compose.smoke.yml` 全套

复制一份意味着 MySQL 参数、字符集、healthcheck、entrypoint 全部出现第二份，日后必然漂移。
用 overlay 叠加，只声明差异项，其余自动继承。

### 3.2 三个必须绕过的坑

**坑 1：`container_name` 是全局唯一的，`-p <project>` 救不了**

compose 的 project name 会隔离网络与卷（`vcc-smoke_mysql_data`），但**不会**给 `container_name` 加前缀。
主栈正在跑时直接起第二套会报：`Conflict. The container name "/vcc-mysql" is already in use`。

→ overlay 里显式覆盖为 `smoke-*`。

**坑 2：compose 的 `ports` 是【追加】，不是替换**

> ⚠️ 本条为**实测更正**。初稿称"按容器端口匹配可替换"（`9f3ffac0` 前的文档版本），实际渲染验证推翻了该结论。

实测结果（overlay 写 `18000`、主文件默认 `8000`）：

```
server ports: [
  {target: 8000, published: '8000'},     ← 主文件的映射照样在
  {target: 8000, published: '18000'}     ← overlay 的，追加而非替换
]
```

这与 `docker-compose.tls.yml` 注释里"`ports: []` 无法移除主文件端口映射"是同一个根因——因为**它是追加，所以空列表等于什么都没做**。

**有效解法（已实测）**：让两条规则**逐字符完全相同**，compose 会去重。

```yaml
# overlay 里照抄主文件的表达式，由 SERVER_PORT 决定最终落到哪个宿主端口
ports:
  - "${SERVER_BIND:-127.0.0.1}:${SERVER_PORT:-8000}:8000"
```

配合 `SERVER_PORT=18000`，渲染结果只剩 1 条 `{published: '18000'}`。

> 注：去重行为属于 compose 的 merge 实现细节，存在版本依赖。即使将来失效，后果也是"同时占 8000 导致容器起不来"——**失败显式可见，不会静默污染生产数据**，风险可接受。

→ smoke 环境把宿主端口换成 18000，避开生产 8000 与网关 8443。

**坑 3：卷会自动隔离，不需要 tmpfs 也不用改 volumes**

加了 `-p vcc-smoke` 后命名卷自动变成 `vcc-smoke_mysql_data`，与生产的 `deploy_mysql_data` 互不相干。
跑完 `down -v` 即彻底销毁。**因此完全不必碰主 compose 的 `volumes`。**

### 3.3 新增文件一：`deploy/docker-compose.smoke.yml`

```yaml
# ============================================================
# 冒烟专用 override —— 一次性、可丢弃的隔离环境
#
# 用法（务必带 -p，卷与网络靠它隔离）：
#   cd deploy
#   ./smoke.sh                 # 一键：起环境 → verify → 拆环境
#
# 手动：
#   docker compose -p vcc-smoke \
#     -f docker-compose.yml -f docker-compose.smoke.yml up -d --wait
#   python3 verify.py --host 127.0.0.1 --port 18000
#   docker compose -p vcc-smoke down -v
#
# 设计要点（每一条都对应一个真实陷阱，改动前请先看第二节 3.2）：
#   1) container_name 是全局唯一的，必须显式改名，否则与主栈冲突
#   2) ports 按容器端口匹配：写 [] 移不掉主文件映射，写同宿端口可替换
#   3) volumes 无需覆盖：-p 已把命名卷变成 vcc-smoke_mysql_data
# ============================================================

services:

  mysql:
    container_name: smoke-mysql
    # 冒烟环境允许弱口令，降低调试摩擦；生产口令不动
    environment:
      MYSQL_ROOT_PASSWORD: smoke_root_only
      MYSQL_DATABASE: ${DB_NAME}
      MYSQL_USER: smoke
      MYSQL_PASSWORD: smoke_only_123

  server:
    container_name: smoke-server
    restart: "no"
    environment:
      DB_IP: mysql
      DB_NAME: ${DB_NAME:-vcc}
      DB_USER: smoke
      DB_PWD: smoke_only_123
    ports:
      # 与主文件【逐字符相同】的 ports 表达式。
      # compose 对 ports 是【追加】而非替换（实测：写了 18000 后渲染结果是
      # 8000 和 18000 两条并存），但只要两条规则完全相同就会去重。
      # 因此这里照抄主文件表达式，由 SERVER_PORT 决定最终发布到哪个宿主端口，
      # 在完全不改主 compose 的前提下把 smoke 挪开、避免与生产栈抢 8000。
      - "${SERVER_BIND:-127.0.0.1}:${SERVER_PORT:-8000}:8000"
```

### 3.4 新增文件二：`deploy/smoke.sh`

一次性麦收：起环境 → 等健康 → 跑 `verify.py` → 无论成败都拆干净。

```bash
#!/usr/bin/env bash
# 冒烟隔离环境：起 → 验 → 拆。失败也会清理，不留脏容器/脏卷。
set -uo pipefail
cd "$(dirname "$0")"

PROJECT="vcc-smoke"
PORT="${SMOKE_PORT:-18000}"

cleanup() { docker compose -p "$PROJECT" down -v >/dev/null 2>&1; }
trap cleanup EXIT

echo "== 起隔离环境 (project=$PROJECT) =="
docker compose -p "$PROJECT" \
  -f docker-compose.yml -f docker-compose.smoke.yml up -d --wait --build || {
  echo "✗ 环境启动失败"; docker compose -p "$PROJECT" logs --tail=40; exit 1; }

echo "== 冒烟 =="
python3 verify.py --host 127.0.0.1 --port "$PORT"
RC=$?

[[ $RC -eq 0 ]] && echo "✓ 冒烟通过" || echo "✗ 冒烟失败 rc=$RC"
exit $RC
```

> `trap cleanup EXIT` 是关键：冒烟失败时也必须销毁，否则失败会留下半死不活的容器占着端口。

## 四、存量脏数据：一次性清理（安全顺序不可颠倒）

15 条历史数据不会因为上了 A 方案就自动消失，需要单独清一次。

```bash
# 1) 先备份 —— 不可省略
docker exec vcc-mysql mysqldump -uroot -p"$MYSQL_ROOT_PWD" vcc \
  > backups/pre-smoke-cleanup-$(date +%Y%m%d-%H%M%S).sql

# 2) dry-run：先看清楚到底要删什么，人工确认无人形
docker exec vcc-mysql mysql -uroot -p"$MYSQL_ROOT_PWD" vcc -e \
  "SELECT id,tel,name,email FROM t_user ORDER BY id;"

# 3) 只有确认全部是冒烟数据后才执行
docker exec vcc-mysql mysql -uroot -p"$MYSQL_ROOT_PWD" vcc -e \
  "DELETE FROM t_user WHERE name LIKE 'smoke\_%' OR email LIKE 'smoke\_%@example.com';"

# 4) 复核
docker exec vcc-mysql mysql -uroot -p"$MYSQL_ROOT_PWD" vcc -e \
  "SELECT COUNT(*) AS remain FROM t_user;"
```

**三条纪律**：

1. 清理条件用 `name` / `email`，**绝不用 `tel LIKE '139%'`**（会误删真实用户，见第二节）。
2. 第 2 步的 dry-run 不可跳过——必须先肉眼确认没有"人样"的账号。
3. 若第 2 步发现存在非冒烟账号，则改为手工逐条指定 `id` 删除。

## 六、实施结果（已真机验证）

已于 2026-10-15 实施并连跑两次，均在**生产栈在线运行**的情况下完成。

| 验证项 | 结果 |
|---|---|
| `smoke.sh` 首次运行 | ✓ 通过 |
| `smoke.sh` 第二次运行（幂等） | ✓ 通过 |
| healthcheck 转 healthy | ✓ `smoke-server Healthy` —— 依赖 `health-probe` |
| 隔离性铁证 | 冒烟注册返回 **`userid=1`**（每次全新空库），生产库自增 ID 已到 15 |
| 生产库污染 | 跑前 15 条 → 第一次后 15 → 第二次后 **15**，零变化 |
| 清理彻底性 | 容器 / `vcc-smoke_mysql_data` 卷 / 18000 端口全部释放 |
| 生产栈影响 | `mysql` `server` `tls-gateway` 全程 healthy，未重启 |

> `userid=1` 这个数字是关键：若误连生产库，自增 ID 应为 16。

### 顺带 closure 的一项阶段 0 遗留

阶段 0 新增的 `health-probe.cpp` 此前**从未真机验证过**（本机 MinGW 缺 `arpa/inet.h`、MSYS2 不完整）。本次构建确认：

- 编译 **0 warning 0 error**，产物 16808 字节
- 容器内实测：连不上时输出 `health-probe: connect 127.0.0.1:8000 错误: Connection refused`，返回码 **3**（非 0 → unhealthy）
- 无参数调用不崩溃，走默认值

> 排查中踩到一个假故障：`docker run <image> ls` 返回 139(SIGSEGV) 一度以为镜像损坏，实际是 `ENTRYPOINT` 为 `playerhallserver`，`ls` 被当成它的入参执行。用 `--entrypoint` 才是正确测法。

## 七、还剩一件事待你确认

**存量 15 条脏数据是否清理。**

隔离方案已杜绝新增，但历史数据不会因为上线新方案而自动消失。我的建议是**暂缓**，理由：

1. 存量清理是一次性运维动作，风险独立，不必和方案上线绑在一起
2. 现在每次冒烟已不碰生产库，脏数据不再增长，没有时间压力
3. 清理动作不可逆，应在需要的时候（例如交付/演示前）一次做完

确认要清时按第四节的顺序执行，`mysqldump` + `SELECT` 肉眼确认两步**不可省略**。
