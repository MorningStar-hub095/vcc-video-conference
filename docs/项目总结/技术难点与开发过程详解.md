### 1.2 技术选型决策过程

#### 1.2.1 UI框架选型

**决策背景：** 需要一个支持跨平台、有丰富GUI组件、支持信号槽机制的C++ UI框架。音视频会议系统的核心特点是事件驱动（音视频帧到达、网络数据接收、用户操作），UI框架必须提供高效的跨线程通信机制，同时需要支持OpenGL渲染上下文嵌入（用于视频画面渲染）。

**选型评估维度：** 项目需求匹配度、信号槽/事件机制成熟度、OpenGL集成能力、跨平台一致性、社区活跃度、团队学习成本。

| 评估维度 | Qt 5.12 | MFC | wxWidgets | Dear ImGui | Electron |
|----------|---------|-----|-----------|------------|----------|
| **跨平台支持** | Win/Mac/Linux/嵌入式 | 仅Windows | Win/Mac/Linux | Win/Mac/Linux | Win/Mac/Linux |
| **信号槽/事件机制** | 原生信号槽，跨线程安全，自动内存管理 | 消息映射宏，Win32消息循环 | 事件表宏，功能类似但文档少 | 无内置事件系统，需自实现 | Node.js事件循环，IPC通信 |
| **OpenGL集成** | QOpenGLWidget无缝嵌入 | 需手动创建GL上下文 | wxGLCanvas支持 | 原生OpenGL渲染 | WebGL支持，但性能受限 |
| **GUI组件丰富度** | 极高（500+组件，Qt Widgets） | 高（Windows原生控件） | 中等（基本控件齐全） | 低（即时模式GUI，适合工具/调试） | 高（HTML/CSS任意布局） |
| **学习曲线** | 中等（信号槽+元对象系统需理解） | 高（Win32 API+MFC宏） | 中等（类似MFC但更简洁） | 低（纯C++，无框架约束） | 低（Web技术栈） |
| **编译产物体积** | 较大（~20MB含Qt库） | 小（~1MB，系统自带） | 中等（~5MB） | 极小（<1MB） | 极大（~100MB含Chromium） |
| **社区活跃度** | 极高（GitHub 2k+ stars，Stack Overflow 100k+问题） | 低（微软已停止新特性开发） | 中等（GitHub 500+ stars） | 高（GitHub 55k+ stars） | 极高（GitHub 110k+ stars） |
| **音视频领域应用案例** | OBS Studio、VLC、Wireshark、TeamViewer | 早期Skype | FileZilla、Audacity | 游戏引擎调试工具 | Discord、Slack、VS Code |
| **长期维护成本** | 低（LTS版本5年支持，商业公司维护） | 高（微软已转向WinUI3） | 中等（志愿者维护） | 低（核心稳定） | 中等（Chromium更新频繁） |
| **团队技术栈适配** | 高（C++原生，与FFmpeg/SDL无缝集成） | 中（C++但API风格老旧） | 中（C++，集成需额外工作） | 高（纯C++） | 低（需JavaScript/TypeScript） |

**淘汰分析：**

- **MFC：** 仅支持Windows，不符合跨平台需求。API设计陈旧（匈牙利命名法、消息映射宏），开发效率低下。微软已将重心转向WinUI3/WPF，MFC长期维护前景不明。
- **wxWidgets：** 虽然跨平台，但社区规模远小于Qt（GitHub stars 2k vs Qt 6k），文档和示例代码不足。信号/事件系统不如Qt成熟，缺少`QThread::moveToThread`等线程安全机制。
- **Dear ImGui：** 即时模式GUI（Immediate Mode GUI），适合工具调试界面，但不适合复杂的对话框式应用（登录界面、房间列表等）。缺少布局管理器，复杂界面实现困难。
- **Electron：** 基于Chromium+Node.js，内存占用高（~200MB起步），不适合对资源敏感的桌面应用。音视频底层操作需要通过Native Addon桥接C++库，增加复杂度和延迟。

**最终选择：** Qt 5.12 + MinGW 32-bit。

**选择依据：**
1. **项目需求匹配度（核心因素）：** Qt的信号槽机制天然适合音视频事件驱动架构。`AudioRead::SIG_audioFrame`、`VideoRead::SIG_sendVideoFrame`等信号可跨线程安全传递，无需手动管理线程同步。Qt的`moveToThread`机制使`SendVideoWorker`等子线程管理变得简单。
2. **OpenGL集成能力：** `QOpenGLWidget`可直接嵌入Qt界面，`QOpenGLFunctions`封装了跨平台OpenGL函数加载，`QOpenGLShaderProgram`简化了GLSL Shader编译。这直接支撑了`YuvGLWidget`的实现。
3. **跨平台一致性：** Qt在Windows/Linux/macOS上提供一致的API和行为，未来可低成本扩展到Linux客户端。
4. **生态系统成熟度：** Qt Creator提供完整的代码编辑、调试、UI Designer工具链，`qmake`构建系统与MinGW工具链配合成熟稳定。
5. **团队技术栈适配：** Qt 5.12是长期支持版本（LTS），C++原生与FFmpeg、SDL2、OpenCV等底层库无缝集成，无跨语言桥接开销。
6. **长期维护成本：** Qt Company提供商业支持和定期安全更新，5.12 LTS支持到2024年。开源版本（LGPLv3）满足项目需求。

#### 1.2.2 视频采集选型

**决策背景：** 需要从摄像头设备获取视频帧数据，支持多平台，API简单。音视频会议系统要求采集延迟低（<33ms@30fps）、支持多种摄像头驱动后端、提供图像预处理能力（缩放、色彩空间转换）。

**选型评估维度：** API简洁度、后端兼容性、延迟表现、图像处理能力、依赖库大小、社区活跃度。

| 评估维度 | OpenCV VideoCapture | DirectShow (COM) | FFmpeg avdevice | GStreamer | libcamera |
|----------|---------------------|-------------------|-----------------|-----------|-----------|
| **API简洁度** | 极高（3行代码采集） | 低（COM接口，数百行初始化） | 低（手动配置设备/格式/管道） | 中（pipeline描述语言） | 中（C API，需理解管线模型） |
| **跨平台支持** | Win/Mac/Linux/嵌入式 | 仅Windows | Win/Mac/Linux | Win/Mac/Linux/嵌入式 | 仅Linux（Raspberry Pi等） |
| **延迟表现** | 低（~16ms@60fps） | 极低（~8ms，原生驱动） | 低（~16ms） | 中（pipeline额外延迟） | 低（~16ms） |
| **后端兼容性** | 多后端回退（MSMF/DSHOW/V4L2） | 仅DirectShow | 需手动指定设备格式 | 自动协商 | 仅V4L2子系统 |
| **图像处理能力** | 极强（cvtColor/resize/滤波/检测） | 无（纯采集） | 无（纯采集） | 有（内置插件） | 无（纯采集） |
| **依赖库大小** | 较大（~50MB核心模块） | 无（系统自带） | 中等（~10MB） | 较大（~30MB） | 小（~2MB） |
| **社区活跃度** | 极高（GitHub 80k+ stars） | 低（微软已停止更新） | 高（GitHub 45k+ stars） | 高（GStreamer社区活跃） | 中（新兴项目） |
| **音视频领域应用** | Zoom、Teams背景虚化 | 早期Skype | VLC、OBS | WebRTC GStreamer后端 | Raspberry Pi摄像头 |
| **团队学习成本** | 低（Python/C++简单API） | 高（COM编程模型） | 高（底层API复杂） | 中（pipeline概念需学习） | 中（新API，文档少） |

**淘汰分析：**

- **DirectShow：** 虽然延迟最低，但仅支持Windows，且COM编程模型复杂度极高（需要实现`ISampleGrabber`、`IGraphBuilder`等接口），开发效率低下。微软已将媒体框架重心转向Media Foundation（MSMF）。
- **FFmpeg avdevice：** 功能强大但API极复杂，需要手动管理设备枚举、格式协商、帧率控制等底层细节。代码量约为OpenCV方案的10倍。适合需要精细控制采集参数的专业场景。
- **GStreamer：** 基于pipeline的流媒体框架，功能强大但学习曲线陡峭。对于简单的摄像头采集场景过于重量级，且在Windows上的摄像头支持不如OpenCV稳定。
- **libcamera：** Linux原生摄像头框架，专为嵌入式设备设计。不支持Windows，适用范围受限。

**最终选择：** OpenCV VideoCapture。

**选择依据：**
1. **API简洁度（核心因素）：** `cap >> frame` 一行代码即可获取摄像头帧，开发效率极高。相比FFmpeg avdevice需要50+行初始化代码，OpenCV大幅缩短开发周期。
2. **多后端回退策略：** OpenCV内部封装了MSMF（Win10+）、DirectShow（Win7）、V4L2（Linux）等多种后端，通过`cv::CAP_MSMF`、`cv::CAP_DSHOW`等参数可指定后端，实现三重回退策略确保兼容性。
3. **图像处理一体化：** 自带`cvtColor`（色彩空间转换）、`resize`（缩放）、`CascadeClassifier`（人脸检测）等功能，无需引入额外图像处理库。BGR→RGB转换、320x240缩放等预处理步骤可在同一框架内完成。
4. **社区与文档：** OpenCV是计算机视觉领域事实标准，Stack Overflow上有超过100k个相关问题，遇到问题几乎都能找到解决方案。
5. **依赖管理：** OpenCV通过`opencv_world4xx.lib`单库链接，Qt Creator中配置简单，无需复杂的依赖管理。

#### 1.2.3 视频编码选型

**决策背景：** 需要将视频帧压缩后通过网络传输，要求高压缩率、低延迟、支持硬件加速。实时视频会议对编码延迟要求极高（<33ms/帧），同时需要在有限带宽下保证画质。

**选型评估维度：** 压缩效率、编码延迟、硬件加速支持、画质表现、兼容性、专利授权、生态系统。

| 评估维度 | H.264 (AVC) | H.265 (HEVC) | VP8/VP9 | AV1 | JPEG |
|----------|-------------|--------------|---------|-----|------|
| **压缩效率** | 高（比JPEG高60%） | 极高（比H.264高40%） | 高（接近H.264） | 极高（比H.265高30%） | 低（无帧间预测） |
| **编码延迟** | 极低（NVENC ~2ms） | 低（NVENC ~5ms） | 中（纯软件~10ms） | 高（纯软件~50ms+） | 极低（<1ms） |
| **硬件加速** | 广泛（NVENC/QSV/AMF/VideoToolbox） | 较广（新一代GPU支持） | 有限（部分QSV支持） | 有限（最新GPU才支持） | 无 |
| **320x240@30fps码率** | 200-500kbps | 150-400kbps | 200-500kbps | 150-350kbps | 2-5Mbps |
| **I帧大小** | 5-15KB | 3-10KB | 5-15KB | 3-10KB | 30-80KB |
| **P帧大小** | 1-5KB | 0.5-3KB | 1-5KB | 0.5-3KB | N/A（全I帧） |
| **浏览器支持** | 全平台支持 | 主流浏览器支持 | Chrome/Firefox支持 | Chrome/Edge支持 | 全平台支持 |
| **专利授权** | 需要（MPEG LA，免费使用） | 复杂（多个专利池） | 免费（Google） | 免费（AOM联盟） | 无 |
| **FFmpeg支持** | 完善 | 完善 | 完善 | 完善 | 完善 |
| **典型应用** | WebRTC、Zoom、Teams、所有视频平台 | 4K流媒体、蓝光 | WebRTC（Chrome默认） | YouTube、Netflix | 监控、截图 |

**淘汰分析：**

- **H.265 (HEVC)：** 压缩效率比H.264高40%，但编码复杂度也高出约50%。专利授权问题复杂（三个独立专利池：MPEG LA、HEVC Advance、Velos Media），商业使用存在法律风险。对于320x240低分辨率场景，压缩效率优势不明显（仅比H.264节省约10-20%带宽），但编码延迟和CPU占用更高。
- **VP8/VP9：** Google开源，免专利费。但硬件加速支持不如H.264广泛（仅部分Intel QSV支持VP8），纯软件编码CPU占用高。VP8的画质在低码率下不如H.264。
- **AV1：** 最新一代开源编码标准，压缩效率最高。但编码复杂度极高（约为H.264的10倍），即使使用SVT-AV1等优化实现，编码延迟仍远超实时要求（>50ms/帧）。硬件加速支持目前仅限最新一代GPU（NVIDIA RTX 40系列、Intel Arc）。
- **JPEG：** 实现最简单，但无帧间预测，每帧独立编码。320x240@30fps需要2-5Mbps带宽，是H.264的10倍以上。适合桌面共享等静态画面场景（本项目中作为桌面共享的编码方案保留）。

**最终选择：** JPEG（初始方案）→ FFmpeg H.264（升级方案）。

**选择依据：**
1. **压缩效率与带宽匹配（核心因素）：** H.264在320x240@30fps下仅需200-500kbps带宽，比JPEG方案降低80%以上。对于局域网和互联网场景，带宽节省直接决定了系统可支持的并发用户数。
2. **硬件加速生态最成熟：** H.264是硬件加速支持最广泛的编码标准。NVIDIA NVENC（GTX 600+）、Intel QSV（Ivy Bridge+）、AMD AMF（GCN+）均原生支持H.264编码，编码延迟低至2ms。本项目实现了`h264_nvenc → h264_qsv → libx264`三级回退链，在任何硬件环境下都能找到最优编码器。
3. **低延迟特性：** H.264的Baseline Profile禁用B帧后，编码延迟可降至单帧级别（~2ms）。`ultrafast`预设+`zerolatency`调优确保libx264软件编码也能满足实时要求。
4. **兼容性最好：** H.264是所有浏览器、操作系统、硬件设备都支持的编码标准，不存在兼容性问题。
5. **渐进式升级策略：** 初始方案使用JPEG快速实现基本功能，验证音视频传输链路后，再升级为H.264。这降低了开发风险，JPEG方案的代码也为桌面共享功能复用。
6. **FFmpeg生态：** FFmpeg提供了统一的H.264编解码API（`avcodec_send_frame`/`avcodec_receive_packet`），硬件编码器和软件编码器使用相同的接口，回退链实现简洁。

#### 1.2.4 音频编码选型

**决策背景：** 需要将音频数据压缩后传输，要求低延迟、高音质、抗丢包。实时语音通话对延迟极其敏感（端到端延迟<150ms），同时需要在低带宽下保证语音可懂度。

**选型评估维度：** 编码延迟、音质（MOS评分）、码率范围、抗丢包能力、CPU占用、维护状态、标准化程度。

| 评估维度 | Opus | Speex | AAC-LD | G.711 | G.729 | LC3 |
|----------|------|-------|--------|-------|-------|-----|
| **采样率范围** | 8-48kHz | 8-32kHz | 16-48kHz | 8kHz | 8kHz | 16-48kHz |
| **编码延迟** | 极低（2.5-20ms） | 低（15-30ms） | 低（20-40ms） | 极低（0.125ms） | 低（15ms） | 极低（2.5-10ms） |
| **MOS音质@32kbps** | 4.2（优秀） | 3.5（良好） | 4.0（良好） | N/A（64kbps） | 3.9（良好） | 4.1（优秀） |
| **最低可用码率** | 6kbps | 8kbps | 32kbps | 64kbps | 8kbps | 16kbps |
| **抗丢包能力** | 极强（内置FEC+PLC） | 弱（需外部FEC） | 中（部分PLC） | 无 | 中（内置PLC） | 强（内置PLC） |
| **DTX静音抑制** | 内置（~1kbps） | 需外部VAD | 无 | 无 | 内置（VAD+DTX） | 内置 |
| **CPU占用@48kHz** | 低（~10MHz ARM） | 低（~5MHz） | 中（~20MHz） | 极低（~1MHz） | 低（~5MHz） | 低（~8MHz） |
| **维护状态** | 活跃（IETF RFC 6716） | 停止（最后更新2014） | 活跃（ISO标准） | 稳定（ITU-T标准） | 稳定（ITU-T标准） | 活跃（Bluetooth SIG） |
| **开源许可** | BSD（完全免费） | BSD | 专利受限 | 专利受限 | 专利受限 | Apache 2.0 |
| **标准化组织** | IETF | Xiph.org | ISO/IEC | ITU-T | ITU-T | Bluetooth SIG |
| **典型应用** | WebRTC/Zoom/Discord/WhatsApp | 早期VoIP | 电话会议/广播 | 传统电话 | 传统电话 | Bluetooth LE Audio |

**淘汰分析：**

- **Speex：** 本项目的初始方案。2014年已被Opus官方宣布为"obsolete"（过时），不再维护。音质在所有码率下均不如Opus，且缺少内置FEC和DTX，需要额外集成WebRTC VAD模块。升级为Opus后代码量减少约30%（移除VAD集成代码）。
- **AAC-LD（Low Delay）：** 为实时通信设计的AAC变种，音质优秀。但编码延迟（20-40ms）高于Opus（2.5-20ms），且专利授权问题复杂。CPU占用约为Opus的2倍。主要应用于Apple FaceTime。
- **G.711：** 传统电话标准，音质尚可但码率固定64kbps，无法根据网络状况自适应。无抗丢包能力，丢包5%即严重影响可懂度。不适合互联网环境。
- **G.729：** 专利已过期（2017年），但编码器实现仍受限。音质在8kbps下接近Speex，但远不如Opus。CPU占用低但功能有限。
- **LC3：** Bluetooth LE Audio标准编解码器，专为蓝牙耳机设计。延迟极低，但主要针对蓝牙传输优化，在TCP/IP网络传输场景中无特殊优势。

**最终选择：** Speex（初始方案）→ Opus（升级方案）。

**选择依据：**
1. **综合性能最优（核心因素）：** Opus在所有维度全面超越Speex——同等码率下MOS评分高0.7分（3.5→4.2），编码延迟低50%（15ms→5ms@48kHz），抗丢包能力通过内置FEC实现10%丢包无明显音质下降。
2. **VOIP模式专为语音优化：** `OPUS_APPLICATION_VOIP`模式内置语音活动检测（VAD）、丢包隐藏（PLC）、不连续传输（DTX）等功能，静音时带宽从32kbps降至约1kbps，大幅节省网络带宽。
3. **自适应码率：** Opus支持6kbps-510kbps动态码率调整，可根据网络状况实时切换。本项目使用32kbps（宽带语音推荐码率），在48kHz采样率下音质接近有线电话。
4. **标准化与开源：** IETF RFC 6716标准，BSD完全开源免费，无专利风险。WebRTC标准强制要求支持Opus，所有主流浏览器和通信平台均已采用。
5. **维护活跃：** Xiph.org和IETF持续维护，定期发布优化和bug修复。社区活跃，遇到问题有丰富的技术资源。
6. **与SDL完美配合：** Opus原生支持48kHz采样率，与SDL2音频回调的48kHz/960samples配置完美匹配，无需重采样。

#### 1.2.5 音频采集选型

**决策背景：** 需要从麦克风设备获取PCM音频数据，要求低延迟、跨平台、帧长固定。音频采集是实时语音通话的第一环，采集延迟和帧长精度直接影响后续编码和传输质量。

**选型评估维度：** 回调机制、延迟精度、跨平台一致性、帧长控制、与播放器统一性、API复杂度。

| 评估维度 | SDL2 Audio | QAudioInput (Qt) | PortAudio | WASAPI (Windows) | CoreAudio (macOS) |
|----------|------------|-------------------|-----------|-------------------|-------------------|
| **回调机制** | 系统级音频线程回调 | QTimer轮询或QIODevice | 系统级回调 | 系统级回调 | 系统级回调 |
| **延迟精度** | 极高（±0.5ms） | 低（±5ms，取决于QTimer） | 高（±1ms） | 极高（±0.1ms） | 极高（±0.1ms） |
| **最低延迟** | ~10ms | ~20ms | ~5ms | ~3ms | ~3ms |
| **帧长控制** | 固定（samples参数精确控制） | 不固定（bytesReady()动态变化） | 固定 | 固定 | 固定 |
| **跨平台支持** | Win/Mac/Linux/移动端 | Win/Mac/Linux | Win/Mac/Linux | 仅Windows | 仅macOS |
| **采集+播放统一** | 统一API（SDL_OpenAudioDevice） | 采集和播放分离API | 统一API | 仅系统API | 仅系统API |
| **与Qt集成** | 需要SDL_Init(SDL_INIT_AUDIO) | 原生集成 | 需要额外初始化 | 需要COM初始化 | 需要额外框架 |
| **API复杂度** | 低（~20行代码） | 低（~15行代码） | 中（~40行代码） | 高（~80行代码） | 高（~80行代码） |
| **48kHz原生支持** | 是 | 是（需验证设备支持） | 是 | 是 | 是 |
| **社区活跃度** | 高（GitHub 9k+ stars） | 高（Qt社区） | 中（GitHub 800+ stars） | N/A（系统API） | N/A（系统API） |
| **典型应用** | 游戏引擎/OBS/VLC | Qt多媒体应用 | 专业音频软件 | Windows专业音频 | macOS专业音频 |

**淘汰分析：**

- **QAudioInput (Qt)：** 本项目的初始方案。虽然与Qt原生集成，但存在关键缺陷：(1) QTimer轮询精度在Windows下仅±5ms，导致采集帧长不固定（150-160 samples不等），Opus/Speex编码器要求固定帧长输入；(2) 跨平台后端不一致（Windows用DirectSound、Linux用ALSA），缓冲区大小和延迟行为不同；(3) 采集和播放使用不同API（QAudioInput/QAudioOutput），维护成本高。
- **PortAudio：** 专业音频I/O库，支持ASIO/WASAPI/CoreAudio等多种后端。API比SDL更底层，需要手动管理缓冲区和回调。对于本项目的简单采集需求过于复杂，且社区规模远小于SDL。
- **WASAPI (Windows Audio Session API)：** Windows原生低延迟音频API，延迟可低至3ms。但仅支持Windows，且需要COM初始化和事件驱动模型，代码量约为SDL方案的4倍。适合专业音频软件（DAW），不适合跨平台通信应用。
- **CoreAudio (macOS)：** macOS原生音频API，延迟极低。但仅支持macOS，且Objective-C API与C++项目集成需要额外桥接工作。

**最终选择：** QAudioInput（初始方案）→ SDL2 Audio（升级方案）。

**选择依据：**
1. **回调驱动精度（核心因素）：** SDL2的`audioCallback`由系统级音频线程触发，延迟精度±0.5ms，帧长精确固定为960 samples（20ms@48kHz）。这解决了QTimer轮询导致的帧长不一致问题，Opus编码器不再因输入帧长变化而报错。
2. **采集播放统一架构：** SDL2使用同一个`SDL_OpenAudioDevice` API处理采集和播放，仅通过`iscapture`参数区分方向。AudioRead和AudioWrite使用相同的SDL配置（48kHz/AUDIO_S16LSB/960samples），架构对称、维护简单。
3. **跨平台一致性：** SDL2在Windows（WASAPI/DirectSound）、Linux（ALSA/PulseAudio）、macOS（CoreAudio）上提供一致的行为和延迟特性，无需针对不同平台编写适配代码。
4. **Qt兼容性：** SDL2仅初始化音频子系统（`SDL_Init(SDL_INIT_AUDIO)`），不接管主线程事件循环，与Qt信号槽机制共存无冲突。已验证在Qt 5.12 + MinGW 32-bit环境下稳定运行。
5. **社区验证：** SDL2在OBS Studio、VLC、Steam等大型项目中广泛使用，音频子系统的稳定性和兼容性经过充分验证。

#### 1.2.6 视频渲染选型

**决策背景：** 需要将解码后的YUV420P数据渲染到屏幕上，要求高性能、低CPU占用、支持多路视频同时显示。每路视频30fps，多路视频同时渲染时CPU不能成为瓶颈。

**选型评估维度：** 渲染性能、CPU占用、YUV直接渲染能力、色彩空间转换、与Qt集成、学习曲线、跨平台支持。

| 评估维度 | OpenGL + GLSL | QPainter (Qt) | DirectX 11 | Vulkan | GDI+ |
|----------|---------------|----------------|------------|--------|------|
| **渲染方式** | GPU硬件加速 | CPU软件渲染 | GPU硬件加速 | GPU硬件加速 | CPU软件渲染 |
| **YUV直接渲染** | 支持（三纹理+Shader） | 不支持（需先转RGB） | 支持（Texture+Shader） | 支持（Image+Compute Shader） | 不支持（需先转RGB） |
| **色彩空间转换** | GPU Fragment Shader（零CPU开销） | CPU逐像素计算（高CPU占用） | GPU Pixel Shader | GPU Compute Shader | CPU逐像素计算 |
| **320x240@30fps CPU占用** | <2% | ~15% | <2% | <1% | ~15% |
| **4路同时渲染CPU占用** | <5% | ~50% | <5% | <3% | ~50% |
| **与Qt集成** | QOpenGLWidget无缝嵌入 | Qt原生API | 需要HWND窗口 | 需要QWindow+Vulkan实例 | 需要GDI DC |
| **学习曲线** | 中等（Shader+纹理概念） | 低（Qt绘图API） | 高（COM+HLSL） | 极高（显式内存管理） | 低（GDI绘图API） |
| **跨平台支持** | Win/Mac/Linux | Win/Mac/Linux | 仅Windows | Win/Mac/Linux | 仅Windows |
| **纹理上传** | glTexImage2D（简单） | N/A | D3D11 CreateTexture | vkCreateImage | N/A |
| **社区资源** | 极多（OpenGL教程/示例） | 多（Qt文档） | 多（微软文档） | 中等（较新API） | 少（已过时） |
| **典型应用** | VLC/OBS/游戏引擎 | Qt桌面应用 | 游戏引擎/视频播放器 | 高性能图形应用 | 早期Windows应用 |

**淘汰分析：**

- **QPainter (Qt)：** 虽然实现最简单（`QPainter::drawImage`一行代码），但使用CPU进行色彩空间转换和缩放，每帧需要将YUV420P数据逐像素转换为RGB，320x240@30fps下CPU占用约15%，4路视频同时渲染时CPU占用超过50%，严重影响其他模块性能。
- **DirectX 11：** 性能与OpenGL相当，但仅支持Windows。需要通过WinAPI获取窗口句柄（HWND），与Qt的`QOpenGLWidget`集成方式不同，需要额外的窗口管理代码。HLSL Shader语言与GLSL不通用，维护成本增加。
- **Vulkan：** 最新一代图形API，性能最优。但API极复杂（显式内存管理、同步原语、管线状态对象等），学习曲线极陡。对于简单的2D视频渲染场景，Vulkan的复杂度完全不必要。一个基本的Vulkan渲染管线需要1000+行代码，而OpenGL仅需200行。
- **GDI+：** Windows GDI的增强版，CPU软件渲染。与QPainter类似存在CPU占用高的问题，且仅支持Windows。已属于过时技术。

**最终选择：** OpenGL + GLSL Shader（通过QOpenGLWidget集成）。

**选择依据：**
1. **GPU渲染零CPU开销（核心因素）：** YUV420P数据直接作为三张纹理（Y/U/V）上传GPU，Fragment Shader在GPU上完成BT.601色彩空间转换，CPU仅负责纹理上传（~0.1ms/帧），不参与逐像素计算。
2. **多路视频扩展性：** 4路视频同时渲染时，CPU占用仍低于5%（每路仅纹理上传开销），GPU并行处理所有色彩转换和渲染。这是QPainter方案无法实现的。
3. **QOpenGLWidget无缝集成：** Qt的`QOpenGLWidget`继承自`QWidget`，可直接放入`QVBoxLayout`布局中，与其他Qt控件（按钮、标签等）无缝共存。`QOpenGLFunctions`封装了跨平台OpenGL函数加载，`QOpenGLShaderProgram`简化了Shader编译。
4. **三纹理YUV420P方案成熟：** 将Y/U/V三个分量分别作为`GL_RED`格式纹理上传，Fragment Shader通过`sampler2D`采样三个纹理并转换为RGB，是业界标准的YUV渲染方案。BT.601标准转换矩阵广泛使用，无需自行推导。
5. **跨平台一致性：** OpenGL在Windows/Linux/macOS上提供一致的API和渲染行为，未来扩展到Linux客户端无需修改渲染代码。
6. **社区资源丰富：** OpenGL是最广泛使用的图形API，教程、示例、调试工具（RenderDoc、apitrace）极其丰富。

#### 1.2.7 网络传输选型

**决策背景：** 需要在客户端和服务端之间传输音视频数据和控制信令，要求可靠传输、低延迟、支持二进制数据。音视频会议系统对网络传输的核心需求是：信令必须可靠送达（不能丢失），音视频数据优先保证实时性（少量丢包可接受）。

**选型评估维度：** 可靠性、延迟、实现复杂度、二进制支持、NAT穿透、拥塞控制、适用场景。

| 评估维度 | TCP (Winsock2) | UDP + RTP/RTCP | WebSocket | QUIC | WebRTC DataChannel | gRPC |
|----------|----------------|----------------|-----------|------|--------------------|----|
| **可靠性** | 极高（内建重传+排序） | 需自实现重传机制 | 高（基于TCP） | 高（内建重传+排序） | 可配置（可靠/不可靠） | 高（基于TCP/HTTP2） |
| **传输延迟** | 中等（拥塞时队头阻塞） | 低（无队头阻塞） | 中等（基于TCP） | 低（多路复用无队头阻塞） | 低（SCTP over DTLS） | 中等（基于HTTP2） |
| **实现复杂度** | 低（标准socket API） | 高（需实现RTP/RTCP/重传/排序） | 中（需HTTP升级握手） | 高（需QUIC库） | 中（需WebRTC库） | 中（需gRPC+Protobuf） |
| **二进制数据支持** | 原生支持 | 原生支持 | 支持（binary frame） | 原生支持 | 原生支持 | 原生支持（Protobuf） |
| **NAT穿透** | 需要（客户端直连服务端） | 需要STUN/TURN | 需要（通过HTTP代理） | 内建连接迁移 | 内建ICE/STUN/TURN | 需要 |
| **拥塞控制** | 内建（但不适合实时媒体） | 需自实现 | 继承TCP拥塞控制 | 内建（优于TCP） | 内建（GCC算法） | 继承TCP拥塞控制 |
| **多路复用** | 不支持（需多连接） | 不支持（需多端口） | 不支持（单连接） | 支持（单连接多流） | 支持（多DataChannel） | 支持（HTTP2多路复用） |
| **依赖库大小** | 无（系统API） | 需RTP库（~500KB） | 无（系统API） | 需QUIC库（~2MB） | 需WebRTC（~50MB） | 需gRPC+Protobuf（~10MB） |
| **适合场景** | 文件传输/信令/可靠数据 | 实时音视频 | 浏览器通信 | 新一代可靠传输 | 浏览器P2P通信 | 微服务/RPC调用 |
| **典型应用** | HTTP/FTP/邮件 | RTP电话/视频会议 | WebSocket聊天/推送 | HTTP3/QUIC视频 | WebRTC P2P | gRPC微服务 |

**淘汰分析：**

- **UDP + RTP/RTCP：** 实时音视频传输的业界标准方案（WebRTC底层即基于RTP）。但实现复杂度极高，需要自定义RTP包头、RTCP反馈、丢包重传、序列号排序、时间戳同步等机制。对于本项目（局域网+TCP三路分离已满足需求），RTP的实现成本过高。未来若需支持互联网场景，可升级为RTP方案。
- **WebSocket：** 基于TCP的全双工通信协议，设计目标是浏览器与服务端的持久连接。对于C++桌面应用，WebSocket的HTTP升级握手和帧格式解析增加了不必要的开销。且底层仍是TCP，无法解决队头阻塞问题。
- **QUIC：** Google开发的基于UDP的可靠传输协议，是HTTP/3的底层协议。多路复用无队头阻塞、内建TLS 1.3加密、连接迁移等特性非常优秀。但C++实现库（msquic/quiche）成熟度不足，且对于局域网场景性能优势不明显。
- **WebRTC DataChannel：** 基于SCTP over DTLS，支持可靠和不可靠两种模式。但WebRTC库体积庞大（~50MB），且需要ICE/STUN/TURN服务器支持，部署复杂度高。适合P2P场景，不适合本项目的C/S架构。
- **gRPC：** 基于HTTP/2的RPC框架，适合微服务间通信。Protobuf序列化效率高，但对实时音视频流传输不是最优选择（HTTP/2的流控机制不适合连续媒体数据）。

**最终选择：** TCP（Winsock2）+ 三路TCP分离架构。

**选择依据：**
1. **实现简单可靠（核心因素）：** TCP是操作系统内核实现的可靠传输协议，无需自定义重传、排序、丢包检测机制。标准socket API（`connect`/`send`/`recv`）在Windows（Winsock2）和Linux上行为一致，开发和调试效率高。
2. **三路TCP分离解决队头阻塞：** 通过为信令、音频、视频分别建立独立TCP连接，避免了大数据包（视频帧~4KB/片）阻塞小数据包（音频帧~100字节、信令包~50字节）的问题。信令连接保证控制指令即时响应，音视频连接保证数据连续传输。
3. **局域网环境适配：** 本项目部署在局域网环境（192.168.x.x），网络延迟<1ms，丢包率接近0。TCP的拥塞控制和重传机制在局域网中几乎不会引入额外延迟，队头阻塞问题在低延迟网络中影响极小。
4. **4字节包头+循环解析处理粘包：** TCP粘包问题通过简单的4字节长度包头+循环接收+memmove方案解决，代码量约30行，逻辑清晰可靠。
5. **TCP_NODELAY优化：** 禁用Nagle算法后，`send`调用立即将数据发送到网络，不等待合并小包。对于音视频小包（100字节~4KB），发送延迟从200ms（Nagle默认延迟）降至<1ms。
6. **渐进式升级路径：** 当前TCP方案满足局域网需求。若未来需支持互联网场景，可渐进升级：TCP → UDP+RTP（添加重传和排序机制）→ WebRTC（完整P2P方案）。三路TCP分离的架构设计为升级提供了清晰的切入点。

#### 1.3.2 技术选型演进路径

#### 1.3.3 技术选型决策方法论

本项目的技术选型遵循以下决策框架：

1. **需求驱动：** 每项技术选型都从具体的功能需求和性能需求出发，避免技术驱动的过度设计。
2. **渐进式升级：** 初始方案选择实现最简单的技术（JPEG/Speex/QAudioInput），快速验证音视频传输链路。验证成功后再逐项升级为性能更优的方案（H.264/Opus/SDL2）。
3. **回退链设计：** 关键模块（H.264编码器/解码器、摄像头采集）采用回退链策略，确保在不同硬件环境下都能正常工作。
4. **统一架构：** 音频采集和播放统一使用SDL2，减少API碎片化。视频渲染统一使用OpenGL，避免QPainter和OpenGL混用。
5. **社区验证：** 优先选择在OBS、VLC、WebRTC等大型项目中经过验证的技术方案，降低技术风险。

## 二、架构设计

### 2.1 分层架构设计

采用 **六层架构** 设计，各层职责明确、接口清晰：

```
┌─────────────────────────────────────────────────┐
│                    UI层                           │
│  LoginDialog / VCC视频会议Dialog / RoomDialog / UserShow │
├─────────────────────────────────────────────────┤
│                  核心调度层                        │
│              ckernel（中介者）                     │
├─────────┬─────────┬──────────┬──────────────────┤
│  音频层  │  视频层  │  编解码层 │    渲染层         │
│AudioRead│VideoRead│H264Encoder│  YuvGLWidget     │
│AudioWrite│ScreenRead│H264Decoder│ MyOpenGLWidget  │
├─────────┴─────────┴──────────┴──────────────────┤
│                  同步层                           │
│         AVSyncManager + SyncContext              │
├─────────────────────────────────────────────────┤
│                  网络层                           │
│    INetMediator → TcpClient / TcpServer          │
├─────────────────────────────────────────────────┤
│                  工具层                           │
│         MD5 / ThreadWorker / SpeexEncoder        │
└─────────────────────────────────────────────────┘
```

**设计原则：**
- **单向依赖：** 上层依赖下层，下层不依赖上层
- **接口隔离：** 通过接口类（INet, INetMediator）隔离实现细节
- **中介者解耦：** ckernel作为中介者，所有跨层通信经过ckernel转发

### 2.2 设计模式应用

#### 2.2.1 接口模式（Interface Pattern）

**应用位置：** 网络层 INet 接口

```cpp
// INet.h - 网络接口定义
class INet
{
public:
    virtual bool InitNet() = 0;                          // 初始化网络
    virtual bool SendData(unsigned int, char*, int) = 0; // 发送数据
    virtual void UnInitNet() = 0;                        // 释放资源
    virtual ~INet() {}
};
```

**设计意义：** TcpClient、TcpServer、UdpNet 均实现 INet 接口，上层代码（INetMediator）仅依赖接口，不关心具体实现。更换网络协议时只需替换实现类，无需修改上层代码。

#### 2.2.2 中介者模式（Mediator Pattern）

**应用位置：** ckernel 类

```cpp
// ckernel.h - 核心中介者
class ckernel : public QObject
{
    Q_OBJECT
private:
    INetMediator* m_pClient;        // 信令连接
    INetMediator* m_pAVClient[3];   // 音视频连接
    VCC视频会议Dialog* m_pVCC视频会议Dlg;     // 主界面
    LoginDialog* m_pLoginDlg;       // 登录界面
    RoomDialog* m_pRoomdialog;      // 房间界面
    AudioRead* m_pAudioRead;        // 音频采集
    AudioWrite* m_pAudioWrite;      // 音频播放
    VideoRead* m_pVideoRead;        // 视频采集
    H264Encoder* m_h264Encoder;     // H264编码器
    // ... 所有模块指针集中管理

    // 协议映射表 - O(1)协议分发
    PFUN m_netPackMap[100];
};
```

**设计意义：** 所有模块之间不直接通信，全部通过ckernel的信号槽和协议映射表转发。例如AudioRead的音频帧通过 `SIG_audioFrame` 信号发送到ckernel，ckernel再调用网络层发送。这避免了模块间的网状依赖。

#### 2.2.3 策略模式（Strategy Pattern）

**应用位置：** 协议分发映射表

```cpp
// ckernel.cpp - 协议映射表初始化
void ckernel::setNetPackMap()
{
    memset(m_netPackMap, 0, sizeof(m_netPackMap));
    m_netPackMap[DEF_PACK_LOGIN_RQ]        = &ckernel::slot_dealLoginRS;
    m_netPackMap[DEF_PACK_REGISTER_RQ]     = &ckernel::slot_dealRegisterRS;
    m_netPackMap[DEF_PACK_CREATEROOM_RQ]   = &ckernel::slot_dealCreateRoomRS;
    m_netPackMap[DEF_PACK_JOINROOM_RQ]     = &ckernel::slot_dealJoinRoomRS;
    m_netPackMap[DEF_PACK_LEAVEROOM_RQ]    = &ckernel::slot_dealLeaveRoomRq;
    m_netPackMap[DEF_PACK_ROOM_MEMBER_RQ]  = &ckernel::slot_dealRoomMemberRq;
    m_netPackMap[DEF_PACK_AUDIO_FRAME_RQ]  = &ckernel::slot_dealAudioFrameRq;
    m_netPackMap[DEF_PACK_VIDEO_FRAME_RQ]  = &ckernel::slot_dealVideoFrameRq;
    m_netPackMap[DEF_PACK_VIDEO_FRAME_H264]= &ckernel::slot_dealVideoFrameH264Rq;
    m_netPackMap[DEF_PACK_PLI_REQUEST]     = &ckernel::slot_dealPliRequestRq;
}

// 数据到达时的分发逻辑 - O(1)查找
void ckernel::slot_dealData(unsigned int sock, char* szbuf, int nlen)
{
    PackType type = *(PackType*)szbuf;
    if (type < sizeof(m_netPackMap)/sizeof(m_netPackMap[0]) && m_netPackMap[type]) {
        (this->*m_netPackMap[type])(sock, szbuf, nlen);  // 函数指针调用
    }
}
```

**设计意义：** 使用函数指针数组替代if-else链，协议分发时间复杂度为O(1)。新增协议只需添加一行映射代码，无需修改分发逻辑。

#### 2.2.4 生产者-消费者模式

**应用位置：** 音频播放队列

```cpp
// audiowrite.h
class AudioWrite : public QObject
{
private:

// 生产者（TCP接收线程 → Qt信号槽 → 主线程slot）
```

**设计意义：** TCP接收线程（生产者）和SDL回调线程（消费者）通过线程安全队列解耦，生产者只管入队，消费者只管出队，互不阻塞。

### 2.3 协议设计

#### 2.3.1 统一包头格式

所有协议包采用统一的二进制包头格式：

```
┌──────────┬──────────┬──────────┬──────────────────┐
│ 4字节包长 │ PackType │  userId  │    业务字段...     │
│ (int)    │  (int)   │  (int)   │   (变长)          │
└──────────┴──────────┴──────────┴──────────────────┘
```

- **4字节包长：** 整个包的字节数（含包头），用于TCP粘包处理
- **PackType：** 协议类型标识，用于映射表分发
- **userId：** 发送者ID，用于识别数据来源

#### 2.3.2 三路TCP分离设计

```
客户端A                              服务端
┌─────────┐    TCP连接1（信令）    ┌──────────┐
│ LoginReq │──────────────────────→│ clogic   │
│ RoomCtrl │←──────────────────────│ 协议分发  │
└─────────┘                        │          │
┌─────────┐    TCP连接2（音频）    │ 房间管理  │
│ AudioFrame│─────────────────────→│          │
└─────────┘    ←───────────────────│          │
┌─────────┐    TCP连接3（视频）    │          │
│ VideoFrame│─────────────────────→│          │
│ H264Frame │←─────────────────────│          │
└─────────┘                        └──────────┘
```

**设计理由：**
- 音视频数据量大且持续（音频~4.5KB/s，视频~120KB/s），如果与信令混用，会导致登录/房间操作等信令延迟
- 三路分离后，信令连接不受音视频数据流影响，保证控制指令即时响应
- 服务端通过 `UserInfo` 结构体维护每个用户的三个socket：
```cpp
struct UserInfo {
    int m_sock;      // 信令socket
    int m_audiofd;   // 音频socket
    int m_videofd;   // 视频socket
};
```

## 三、网络模块开发

### 3.1 TCP客户端实现

#### 3.1.1 核心数据结构

```cpp
// TcpClient.h
class TcpClient : public INet
{
private:
    SOCKET m_sock;              // 主连接socket
    HANDLE m_hThread;           // 接收线程句柄
    bool m_isConnected;         // 连接状态标志
    char m_szRecvBuf[40960];    // 接收缓冲区（40KB，防粘包溢出）
    int m_nOffset;              // 缓冲区当前偏移量
};
```

**设计决策：**
- `m_szRecvBuf[40960]`（40KB缓冲区）：视频帧可能接近1MB，但通过分片后单片仅4KB+包头，40KB足够容纳多个分片
- `m_nOffset`：记录缓冲区中已接收但未处理的字节数，处理TCP粘包的关键

#### 3.1.2 连接建立流程

```cpp
bool TcpClient::InitNet()
{
    // 1. 初始化Winsock
    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);

    // 2. 创建socket
    m_sock = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);

    // 3. 设置TCP_NODELAY（禁用Nagle算法，降低延迟）
    int flag = 1;
    setsockopt(m_sock, IPPROTO_TCP, TCP_NODELAY, (char*)&flag, sizeof(flag));

    // 4. 设置收发缓冲区（64KB）
    int bufSize = 64 * 1024;
    setsockopt(m_sock, SOL_SOCKET, SO_SNDBUF, (char*)&bufSize, sizeof(bufSize));
    setsockopt(m_sock, SOL_SOCKET, SO_RCVBUF, (char*)&bufSize, sizeof(bufSize));

    // 5. 连接服务端
    sockaddr_in addr;
    addr.sin_family = AF_INET;
    addr.sin_port = htons(_DEF_TCP_PORT);        // 8000
    addr.sin_addr.s_addr = inet_addr(_DEF_SERVER_IP); // 192.0.2.130
    connect(m_sock, (sockaddr*)&addr, sizeof(addr));

    // 6. 启动接收线程
    m_hThread = (HANDLE)_beginthreadex(NULL, 0, &recvThread, this, 0, NULL);
}
```

**关键配置说明：**
- `TCP_NODELAY`：禁用Nagle算法。Nagle算法会将小包合并为大包再发送，增加延迟。对于实时音视频场景，必须禁用。
- `SO_SNDBUF/SO_RCVBUF = 64KB`：增大发送/接收缓冲区，减少因缓冲区满导致的send阻塞

#### 3.1.3 TCP粘包处理

TCP是字节流协议，没有消息边界。多个协议包可能合并为一个TCP段到达，也可能一个协议包被拆分为多个TCP段。

**解决方案：** 4字节长度包头 + 循环接收

```cpp
unsigned __stdcall TcpClient::recvThread(void* arg)
{
    TcpClient* pThis = (TcpClient*)arg;
    while (pThis->m_isConnected)
    {
        // 第一步：接收数据到缓冲区
        int nRecvNum = recv(pThis->m_sock,
                           pThis->m_szRecvBuf + pThis->m_nOffset,
                           sizeof(pThis->m_szRecvBuf) - pThis->m_nOffset,
                           0);
        if (nRecvNum <= 0) {
            pThis->m_isConnected = false;
            break;
        }
        pThis->m_nOffset += nRecvNum;

        // 第二步：循环解析完整包
        while (pThis->m_nOffset >= (int)sizeof(int))
        {
            // 读取包长
            int nPackSize = *(int*)pThis->m_szRecvBuf;

            // 检查是否收到完整包
            if (pThis->m_nOffset < nPackSize) break;

            // 完整包到达，分发处理
            pThis->m_pMediator->slot_dealData(0, pThis->m_szRecvBuf, nPackSize);

            // 移动剩余数据到缓冲区头部
            pThis->m_nOffset -= nPackSize;
            memmove(pThis->m_szRecvBuf,
                    pThis->m_szRecvBuf + nPackSize,
                    pThis->m_nOffset);
        }
    }
    return 0;
}
```

**处理流程图：**
```
TCP字节流到达：[包1完整][包2前半] → [包2后半][包3完整][包4前半]
                   ↓                        ↓
缓冲区状态：  [包1|包2前半]            [包2后半|包3|包4前半]
                   ↓                        ↓
解析循环：    取出包1，剩余=包2前半     取出包2，取出包3，剩余=包4前半
              继续recv等待              继续recv等待包4后半
```

### 3.2 问题与解决方案

#### 问题1：TCP粘包导致协议解析错误

**现象：** 客户端偶尔收到格式错误的协议包，解析出异常的type字段

**根因分析：**
- TCP是字节流协议，发送端多次send的数据可能在接收端一次recv就收到
- 例如：发送端连续发送 [LOGIN_RS(100字节)] [ROOMMEMBER(50字节)]
- 接收端可能一次recv收到 [LOGIN_RS前80字节 + ROOMMEMBER全部50字节]

**解决方案：** 如3.1.3节所述，4字节包头 + 循环解析 + memmove移动剩余数据

**验证方法：** 在接收端打印每个包的type和size，确认解析正确

#### 问题2：视频帧超过1MB导致缓冲区溢出

**现象：** 大分辨率JPEG帧（如1920x1080）可能超过1MB，发送到服务端后服务端缓冲区溢出

**根因分析：**
- JPEG压缩后仍有约300-500KB，加上包头约1MB
- 服务端接收缓冲区设计为1MB安全阈值

**解决方案：** 发送前检查包大小，超过1MB丢弃该帧
```cpp
// ckernel.cpp - 发送视频帧前的大小检查
void ckernel::slot_sendVideoFrame(QImage img)
{
    // ... 编码为JPEG ...
    QByteArray ba;
    // ... JPEG编码 ...

    if (buflen + sizeof(STRU_VIDEO_FRAME) > 1 * 1024 * 1024) {
        printf("[VideoFrame] 包太大 %d 字节, 跳过该帧\n", buflen);
        return;  // 丢弃超大帧
    }

    // 正常发送
    m_pClient->SendData(0, ba.data(), ba.size());
}
```

#### 问题3：UDP sendto阻塞导致音频卡顿

**现象：** 使用UDP传输音频时，偶尔出现500ms以上的卡顿

**根因分析：**
- UDP sendto在某些情况下会阻塞（如系统发送缓冲区满）
- 音频线程被阻塞后，后续音频帧积压，导致卡顿

**解决方案：** 改用TCP替代UDP。TCP的流控机制天然处理背压，不会出现突发性长阻塞。同时通过三路TCP分离，音频数据不会被视频数据阻塞。

#### 问题4：config.ini IP地址覆盖默认值

**现象：** 修改了 `INetMediator.h` 中的 `_DEF_SERVER_IP` 为新IP，但客户端仍连接旧IP

**根因分析：**
- `ckernel::initConfig()` 先设置默认值，再检查config.ini是否存在
- 如果config.ini存在，用其中的IP覆盖默认值
- 多个构建目录存在不同版本的config.ini，修改代码默认值无效

**解决方案：** 修改所有config.ini文件中的IP地址
```ini
# config.ini
ip=192.0.2.130
port=8000
```

**修改位置：**
- `build-VCC视频会议-Desktop_Qt_5_12_11_MinGW_32_bit-Release\release\config.ini`
- `full_copy_test\config.ini`

```cpp
    format.setChannelCount(1);         // 单声道
    format.setSampleSize(16);          // 16bit位深
    format.setCodec("audio/pcm");      // PCM编码
    format.setByteOrder(QAudioFormat::LittleEndian);
    format.setSampleType(QAudioFormat::SignedInt);

    // 创建QAudioInput
    QAudioDeviceInfo info = QAudioDeviceInfo::defaultInputDevice();
    if (!info.isFormatSupported(format)) {
        format = info.nearestFormat(format);  // 回退到最近格式
    }
    m_audio_in = new QAudioInput(format, this);
    m_buffer_in = m_audio_in->start();  // 开始采集

    // 20ms定时器轮询
    m_timer = new QTimer(this);
    connect(m_timer, &QTimer::timeout, this, &AudioRead::slot_readAudio);
    m_timer->start(20);  // 每20ms读取一次

    // Speex编码器初始化
```

### 4.2 升级方案：SDL2 + Opus

#### 4.2.1 升级动机

参考 `AudioDemo2` 项目中已验证的SDL+Opus方案，决定将VCC视频会议项目的音频模块统一升级为SDL+Opus架构。

#### 4.2.2 SDL2采集架构

```cpp
    m_sdlIsOpen = false;

    }
    // Opus参数配置
    opus_encoder_ctl(m_opusEncoder, OPUS_SET_BITRATE(32000));    // 32kbps
    opus_encoder_ctl(m_opusEncoder, OPUS_SET_COMPLEXITY(5));     // 复杂度5（平衡）
    opus_encoder_ctl(m_opusEncoder, OPUS_SET_INBAND_FEC(1));     // 前向纠错
    opus_encoder_ctl(m_opusEncoder, OPUS_SET_DTX(1));            // 不连续传输

    // WebRTC VAD初始化
    WebRtcVad_Create(&handle);
    WebRtcVad_Init(handle);
    WebRtcVad_set_mode(handle, 1);  // 聚合度1（0-3，越小越敏感）

// SDL回调函数（系统级音频线程调用，每20ms触发）
void AudioRead::audioCallback(void *userdata, Uint8 *stream, int len)
{
    AudioRead *audio = (AudioRead *)userdata;
    if (len < 1920) return;  // 960 samples × 2 bytes = 1920

    // VAD静音检测
    int vadResult = WebRtcVad_Process(audio->handle, 48000,
                                       (const int16_t*)stream, 960);
    if (vadResult == 0) {
        // 静音帧：Opus DTX模式会自动发送极小的SID帧（约10字节）
        // 不需要手动清零，Opus DTX会处理
    }

    // Opus编码
    unsigned char opusData[4096];
    int nbBytes = opus_encode(audio->m_opusEncoder,
                              (const opus_int16*)stream, 960,
                              opusData, sizeof(opusData));
    if (nbBytes < 0) {
        qDebug() << "[Opus] 编码错误:" << opus_strerror(nbBytes);
        return;
    }

    // 通过信号跨线程传递到ckernel
    QByteArray sendBuffer((char*)opusData, nbBytes);
    Q_EMIT audio->SIG_audioFrame(sendBuffer);
}

void AudioRead::start()
{
    if (!m_sdlIsOpen) {
        SDL_AudioSpec desiredSpec, obtainedSpec;
        SDL_zero(desiredSpec);
        desiredSpec.freq     = 48000;           // 48kHz
        desiredSpec.format   = AUDIO_S16LSB;   // 16bit小端
        desiredSpec.channels = 1;              // 单声道
        desiredSpec.samples  = 960;            // 20ms @ 48kHz
        desiredSpec.callback = audioCallback;
        desiredSpec.userdata = this;

        m_sdlCaptureDev = SDL_OpenAudioDevice(NULL, 1,
                            &desiredSpec, &obtainedSpec, 0);
        if (m_sdlCaptureDev == 0) {
            qDebug() << "[SDL-Capture] 打开失败:" << SDL_GetError();
            return;
        }
        m_sdlIsOpen = true;
    }
    SDL_PauseAudioDevice(m_sdlCaptureDev, 0);  // 开始采集
    m_AudioState = playing;
}
```

#### 4.2.4 Opus编码参数详解

| 参数 | 值 | 含义 | 选择理由 |
|------|-----|------|----------|
| `sample_rate` | 48000 | 采样率48kHz | Opus原生优化速率，音质最佳 |
| `channels` | 1 | 单声道 | 语音通话单声道足够 |
| `application` | OPUS_APPLICATION_VOIP | VOIP模式 | 针对语音优化，内置DTX和PLC |
| `bitrate` | 32000 | 32kbps | 宽带语音的推荐码率 |
| `complexity` | 5 | 复杂度5 | 平衡CPU占用和音质（0-10） |
| `INBAND_FEC` | 1 | 前向纠错 | 10%丢包下音质无明显下降 |
| `DTX` | 1 | 不连续传输 | 静音时带宽降至~1kbps |

#### 4.2.5 Opus编码输出大小分析

| 音频内容 | 960 samples (1920字节PCM) → Opus | 压缩率 |
|----------|----------------------------------|--------|
| 正常语音 | ~60-120 字节 | 93-97% |
| 静音(DTX) | ~10 字节 (SID帧) | 99.5% |
| 高能量语音 | ~120-150 字节 | 92-94% |

### 4.3 问题与解决方案

#### 问题5：SDL初始化与Qt事件循环冲突

**现象：** 调用 `SDL_Init(SDL_INIT_AUDIO)` 后，Qt的信号槽机制出现异常，部分信号无法正常传递

**根因分析：**
- SDL默认会初始化视频子系统，接管主线程的事件循环
- Qt也需要主线程事件循环来驱动信号槽机制
- 两者冲突导致Qt事件处理异常

**解决方案：** SDL仅初始化音频子系统，不初始化视频
```cpp
// main.cpp
int main(int argc, char *argv[])
{
    QApplication a(argc, argv);

    // 仅初始化SDL音频子系统，不初始化视频
    if (SDL_Init(SDL_INIT_AUDIO) < 0) {
        qDebug() << "[SDL] SDL_Init(SDL_INIT_AUDIO) failed:" << SDL_GetError();
    } else {
        qDebug() << "[SDL] SDL_Init(SDL_INIT_AUDIO) succeeded";
    }

    // ... 创建ckernel，启动Qt事件循环 ...
    return a.exec();
}
```

#### 问题6：Speex解码后声音断续

**现象：** 接收端播放声音一卡一卡，间隔约50-100ms出现一次断续

**根因分析：**
- QTimer轮询精度不足，Windows下实际间隔为15-25ms（理论20ms）
- 采集帧大小不一致（有时160样本，有时150样本）
- 解码端Speex要求固定帧长，不一致的输入导致解码异常

**解决方案：** 升级为SDL回调驱动。SDL回调由系统级音频线程触发，精度为±0.5ms，且帧长固定为960样本。

**效果对比：**
```
升级前（QTimer）：采集间隔 20ms ±5ms，帧长 150-160 samples（不稳定）
升级后（SDL）：  采集间隔 20ms ±0.5ms，帧长 960 samples（固定）
```

#### 问题7：多人同时说话时音频数据竞争

**现象：** 两个用户同时说话时，接收端偶尔出现音频杂音或崩溃

**根因分析：**
- 多个发送者的音频帧几乎同时通过TCP到达
- ckernel的 `slot_dealAudioFrameRq` 在主线程调用 `m_pAudioWrite->slot_playAudio()`
- SDL回调线程同时调用 `audioCallback` 从队列取数据
- deque无保护的并发读写导致数据竞争

**解决方案：** std::mutex保护deque队列
```cpp
// audiowrite.cpp
std::deque<QByteArray> m_audioQueue;
std::mutex m_mutex;

// 生产者（主线程slot）
void AudioWrite::slot_playAudio(QByteArray bt) {
    std::lock_guard<std::mutex> lck(m_mutex);
    m_audioQueue.emplace_back(bt);
}

// 消费者（SDL回调线程）
void AudioWrite::audioCallback(void *userdata, Uint8 *stream, int len) {
    AudioWrite *audio = (AudioWrite *)userdata;
    memset(stream, 0, len);  // 清零输出缓冲区

    std::lock_guard<std::mutex> lck(audio->m_mutex);
    if (!audio->m_audioQueue.empty()) {
        QByteArray recvBuffer = audio->m_audioQueue.front();
        audio->m_audioQueue.pop_front();

        // Opus解码
        opus_int16 decodedData[4096];
        int frameSize = opus_decode(audio->m_opusDecoder,
                                     (const uchar*)recvBuffer.data(),
                                     recvBuffer.size(),
                                     decodedData, 4096, 0);
        if (frameSize > 0) {
            SDL_MixAudioFormat(stream, (uint8_t*)decodedData,
                               AUDIO_S16LSB,
                               frameSize * sizeof(opus_int16), 100);
        }
    }
}
```

#### 问题8：WebRTC VAD与48kHz采样率兼容性

**现象：** `WebRtcVad_Process` 在48kHz下偶尔返回错误码

**根因分析：**
- WebRTC VAD内部支持8kHz/16kHz/32kHz/48kHz，但需要正确的帧长
- 48kHz下，支持的帧长为480样本(10ms)或960样本(20ms)
- 使用不支持的帧长会返回错误

**解决方案：** 使用前验证采样率和帧长组合
```cpp

if (valid != 0) {
    qDebug() << "[VAD] 48kHz + 960 samples 不支持，回退到480 samples";
    // 回退方案：每480样本调用一次VAD，调用两次覆盖20ms
}
```

#### 5.1.1 OpenCV多后端回退策略

不同Windows版本和驱动环境下，OpenCV的可用后端不同。采用三重回退策略确保兼容性：

```cpp
// videoread.cpp
void VideoRead::slot_openVideo()
{
    bool opened = false;

    // 第一优先：MSMF（Media Foundation，Win10+推荐）
    opened = m_cap.open(0, cv::CAP_MSMF);
    if (opened) {
        qDebug() << "[VideoRead] 使用MSMF后端打开摄像头";
    }

    // 第二优先：DirectShow（Win7兼容性好）
    if (!opened) {
        opened = m_cap.open(0, cv::CAP_DSHOW);
        if (opened) {
            qDebug() << "[VideoRead] 使用DirectShow后端打开摄像头";
        }
    }

    // 第三优先：默认后端（OpenCV自动选择）
    if (!opened) {
        opened = m_cap.open(0);
        if (opened) {
            qDebug() << "[VideoRead] 使用默认后端打开摄像头";
        }
    }

    if (!opened) {
        qDebug() << "[VideoRead] 所有后端均无法打开摄像头";
        return;
    }

    // 设置采集参数
    m_cap.set(cv::CAP_PROP_FRAME_WIDTH, 320);
    m_cap.set(cv::CAP_PROP_FRAME_HEIGHT, 240);
    m_cap.set(cv::CAP_PROP_FPS, 30);

    // 启动20ms定时器采集
    m_timer->start(33);  // 约30fps
}
```

### 5.3 问题与解决方案

#### 问题9：摄像头打开失败（无MSMF后端）

**现象：** 在某些Windows 7机器上，`m_cap.open(0, cv::CAP_MSMF)` 返回false

**根因分析：**
- MSMF（Media Foundation）是Windows 10推荐的媒体框架
- Windows 7默认不支持或支持不完整
- OpenCV编译时可能未包含MSMF后端

**解决方案：** 三重回退策略（MSMF → DirectShow → 默认），如5.1.1节所述

#### 问题10：视频帧发送阻塞UI线程

**现象：** 开启摄像头后，UI界面操作卡顿，点击按钮响应延迟

**根因分析：**
- 摄像头采集回调（33ms间隔）中直接调用TCP发送
- TCP send在发送缓冲区满时会阻塞
- 主线程被阻塞导致UI无响应

**解决方案：** 视频编码和发送分离到独立子线程（SendVideoWorker）
```cpp
// ckernel.cpp
void ckernel::slot_sendVideoFrame(QImage img)
{
    // 主线程：编码（快速操作）
    QByteArray ba;
    if (m_useH264 && m_h264Encoder) {
        m_h264Encoder->encode(img, ba);  // H264编码，约1-2ms
    } else {
        // JPEG编码回退
        QBuffer buf(&ba);
        img.save(&buf, "JPEG", 50);
    }

    // 将数据发送到子线程（非阻塞）
    char* sendData = new char[ba.size()];
    memcpy(sendData, ba.data(), ba.size());
    Q_EMIT m_pSendVideoWorker->SIG_SendVideo(sendData, ba.size());
}

// SendVideoWorker子线程slot
void SendVideoWorker::slot_SendVideo(char* buf, int len)
{
    // 子线程：网络发送（可能阻塞，但不影响UI）
    m_pClient->SendData(0, buf, len);
    delete[] buf;  // 释放临时缓冲区
}
```

#### 问题11：视频帧队列堆积导致内存增长

**现象：** 网络慢时，内存持续增长，最终OOM

**根因分析：**
- 视频采集以30fps固定速率进行
- 网络发送速度低于采集速度时，帧在队列中堆积
- 每帧约100-300KB，1秒堆积30帧约3-9MB

**解决方案：** 子线程中检查队列长度，超过300ms的旧帧直接丢弃
```cpp
void SendVideoWorker::slot_SendVideo(char* buf, int len)
{
    // 300ms丢帧策略：如果发送队列过长，丢弃旧帧
    QMutexLocker locker(&m_mutex);
    if (m_sendQueue.size() > 10) {  // 约300ms @ 30fps
        // 丢弃队列中最旧的帧
        auto old = m_sendQueue.dequeue();
        delete[] old.first;
    }
    m_sendQueue.enqueue({buf, len});
}
```

#### 6.1.1 编码器硬件回退链

```cpp
// h264encoder.cpp
int H264Encoder::init(int width, int height, int fps, int bitrate)
{
    m_width = width;
    m_height = height;

    // 硬件编码器回退链
    const char* encoderNames[] = {
        "h264_nvenc",    // NVIDIA GPU编码（最快）
        "h264_qsv",      // Intel Quick Sync Video
        "libx264",       // 软件编码（最兼容）
        nullptr
    };

    AVCodec* codec = nullptr;
    for (int i = 0; encoderNames[i]; i++) {
        codec = avcodec_find_encoder_by_name(encoderNames[i]);
        if (codec) {
            m_encoderName = encoderNames[i];
            printf("[H264Encoder] 使用编码器: %s\n", encoderNames[i]);
            break;
        }
    }

    // 最终兜底
    if (!codec) {
        codec = avcodec_find_encoder(AV_CODEC_ID_H264);
        m_encoderName = "default_h264";
        printf("[H264Encoder] 使用默认H264编码器\n");
    }

    if (!codec) {
        printf("[H264Encoder] 未找到任何H264编码器！\n");
        return -1;
    }

    // 分配编码器上下文
    m_codecCtx = avcodec_alloc_context3(codec);
    if (!m_codecCtx) return -1;

    // 编码参数配置
    m_codecCtx->width = width;                    // 320
    m_codecCtx->height = height;                  // 240
    m_codecCtx->time_base = {1, fps};             // {1, 30}
    m_codecCtx->framerate = {fps, 1};             // {30, 1}
    m_codecCtx->bit_rate = bitrate;               // 200000 (200kbps)
    m_codecCtx->gop_size = 60;                    // 每2秒一个关键帧
    m_codecCtx->max_b_frames = 0;                 // 禁用B帧（降低延迟）
    m_codecCtx->pix_fmt = AV_PIX_FMT_YUV420P;    // 输入像素格式

    // 仅对libx264设置编码预设
    if (m_encoderName == "libx264") {
        av_opt_set(m_codecCtx->priv_data, "preset", "ultrafast", 0);  // 最快编码速度
        av_opt_set(m_codecCtx->priv_data, "tune", "zerolatency", 0);  // 零延迟模式
        av_opt_set(m_codecCtx->priv_data, "crf", "28", 0);            // 恒定质量因子
    }

    // 设置Baseline Profile（兼容性最好）
    m_codecCtx->profile = FF_PROFILE_H264_BASELINE;

    // 打开编码器
    int ret = avcodec_open2(m_codecCtx, codec, nullptr);
    if (ret < 0) {
        char errBuf[256];
        av_strerror(ret, errBuf, sizeof(errBuf));
        printf("[H264Encoder] avcodec_open2 失败: %s\n", errBuf);
        return ret;
    }

    // 分配帧和包
    m_frame = av_frame_alloc();
    m_frame->format = m_codecCtx->pix_fmt;
    m_frame->width = m_codecCtx->width;
    m_frame->height = m_codecCtx->height;
    av_frame_get_buffer(m_frame, 0);

    m_packet = av_packet_alloc();

    // 创建色彩空间转换器（RGB24 → YUV420P）
    m_swsCtx = sws_getContext(
        m_width, m_height, AV_PIX_FMT_RGB24,    // 输入
        m_width, m_height, AV_PIX_FMT_YUV420P,  // 输出
        SWS_BILINEAR, nullptr, nullptr, nullptr);

    return 0;
}
```

#### 6.1.2 编码流程

```cpp
int H264Encoder::encode(QImage image, QByteArray& outData)
{
    // 1. QImage → RGB24数据
    QImage rgbImage = image.convertToFormat(QImage::Format_RGB888);
    const uint8_t* srcSlice[1] = { rgbImage.bits() };
    int srcStride[1] = { (int)rgbImage.bytesPerLine() };

    // 2. RGB24 → YUV420P（sws_scale处理stride对齐）
    av_frame_make_writable(m_frame);
    sws_scale(m_swsCtx,
              srcSlice, srcStride, 0, m_height,
              m_frame->data, m_frame->linesize);

    // 3. 设置帧时间戳
    m_frame->pts = m_frameSeq++;

    // 4. 送入编码器
    int ret = avcodec_send_frame(m_codecCtx, m_frame);
    if (ret < 0) return ret;

    // 5. 取出编码后的包
    ret = avcodec_receive_packet(m_codecCtx, m_packet);
    if (ret < 0) return ret;

    // 6. 输出H264数据
    outData = QByteArray((char*)m_packet->data, m_packet->size);

    // 7. 释放包引用
    av_packet_unref(m_packet);

    return 0;
}
```

```cpp
{
```

#### 6.2.2 解码流程（零拷贝）

```cpp
int H264Decoder::decode(QByteArray data, AVFrame** outFrame)
{
    // 1. 零拷贝包装QByteArray数据（不复制数据）
    av_packet_from_data(m_packet,
                        (uint8_t*)data.data(),
                        (int)data.size());

    // 2. 送入解码器
    int ret = avcodec_send_packet(m_codecCtx, m_packet);
    av_packet_unref(m_packet);  // 立即释放包引用（数据已被解码器内部引用）
    if (ret < 0) return ret;

    // 3. 取出解码帧
    ret = avcodec_receive_frame(m_codecCtx, m_frame);
    if (ret < 0) return ret;

    // 4. 克隆帧（引用计数+1），用于跨模块传递
    *outFrame = av_frame_clone(m_frame);

    // 5. 释放原始引用（解码器内部引用-1）
    av_frame_unref(m_frame);

    return 0;
}
```

```cpp
// ckernel.cpp - 接收H264分片并重组
void ckernel::slot_dealVideoFrameH264Rq(int sock, char* szbuf, int nlen)
{
    STRU_VIDEO_FRAME_H264_HEADER* header = (STRU_VIDEO_FRAME_H264_HEADER*)szbuf;
    char* h264Data = szbuf + sizeof(STRU_VIDEO_FRAME_H264_HEADER);
    int dataSize = nlen - sizeof(STRU_VIDEO_FRAME_H264_HEADER);

    int userId = header->m_userid;
    int frameSeq = header->m_frameSeq;
    int totalFragments = header->m_totalFragments;
    int fragmentIndex = header->m_fragmentIndex;

    // 获取或创建该用户的重组缓冲区
    auto& fragMap = m_mapIDToH264Fragments[userId];
    auto& fragVec = fragMap[frameSeq];

    // 存储分片
    if (fragVec.size() <= fragmentIndex) {
        fragVec.resize(fragmentIndex + 1);
    }
    fragVec[fragmentIndex] = QByteArray(h264Data, dataSize);

    // 检查是否收齐所有分片
    int receivedCount = 0;
    for (const auto& frag : fragVec) {
        if (!frag.isEmpty()) receivedCount++;
    }

    if (receivedCount == totalFragments) {
        // 重组完整帧
        QByteArray fullFrame;
        for (const auto& frag : fragVec) {
            fullFrame.append(frag);
        }
        fragMap.erase(frameSeq);  // 清理分片缓冲

        // 解码完整帧
        AVFrame* decodedFrame = nullptr;
        if (m_mapIDToH264Decoder[userId]) {
            m_mapIDToH264Decoder[userId]->decode(fullFrame, &decodedFrame);
            if (decodedFrame) {
                // 传递到RoomDialog进行渲染
                m_pRoomdialog->slot_refreshUserYuv(userId, decodedFrame);
            }
        }
    }
}
```

### 6.3 问题与解决方案

#### 问题12：NVENC编码器找不到

**现象：** 日志输出 `[H264Encoder] 使用编码器: libx264`，未使用硬件编码

**根因分析：**
- 系统没有NVIDIA显卡，或驱动版本过旧不支持NVENC
- FFmpeg编译时未包含NVENC支持

**解决方案：** 回退链自动处理，无需手动干预。如果需要强制使用硬件编码：
1. 更新NVIDIA驱动到最新版本
2. 确认FFmpeg编译时启用了 `--enable-nvenc`

#### 问题13：编码后画面绿色/花屏

**现象：** 解码后画面底部有绿色条纹，或整体花屏

**根因分析：**
- QImage的 `bytesPerLine()` 可能不是 `width * 3` 的整数倍（存在padding）
- sws_scale的srcStride参数设置错误，导致色彩空间转换时数据错位

**解决方案：** 使用QImage的实际bytesPerLine作为stride
```cpp
// 正确：使用bytesPerLine()而不是width*3
const uint8_t* srcSlice[1] = { rgbImage.bits() };
int srcStride[1] = { (int)rgbImage.bytesPerLine() };  // 关键：用bytesPerLine()

sws_scale(m_swsCtx, srcSlice, srcStride, 0, m_height,
          m_frame->data, m_frame->linesize);
```

#### 问题14：新成员加入房间时画面花屏

**现象：** 用户B加入房间后，看到的第一帧视频画面花屏，之后逐渐恢复正常

**根因分析：**
- 用户B加入时，收到的视频帧是P帧（预测帧）
- P帧需要参考前一帧才能正确解码
- 用户B没有前一帧作为参考，因此P帧解码失败

**解决方案：** PLI关键帧请求机制
```cpp
// ckernel.cpp - 新成员加入房间后
void ckernel::slot_dealRoomMemberRq(int sock, char* szbuf, int nlen)
{
    // ... 解析新成员信息 ...

        m_h264Encoder->requestKeyFrame();
    }

    pli.m_userid = m_id;
    pli.m_roomid = m_roomid;
    m_pClient->SendData(0, (char*)&pli, sizeof(pli));
}
```

#### 问题15：AVFrame引用计数导致的use-after-free

**现象：** 长时间通话后偶发崩溃，崩溃位置在访问AVFrame数据时

**根因分析：**
- 代码中对同一AVFrame调用了两次 `av_frame_free`
- 第一次free后refcount=0，内存被释放
- 第二次free或访问导致use-after-free

**正确的引用计数传递链：**
```
H264Decoder::decode()
    ├── avcodec_receive_frame() → frame (refcount=1)
    ├── av_frame_clone()        → sharedFrame (refcount=2)
    ├── av_frame_unref()        → frame释放 (sharedFrame refcount=1)
    └── return sharedFrame
            │
            ▼
        ckernel → RoomDialog → UserShow
            │
            ├── av_frame_clone() → renderFrame (refcount=2)
            ├── av_frame_free(sharedFrame) → sharedFrame释放 (renderFrame refcount=1)
            │
            ▼
        YuvGLWidget::slot_setFrame()
            ├── 上传纹理到GPU
            └── av_frame_free(renderFrame) → renderFrame释放 (refcount=0, 内存回收)
```

**关键规则：**
1. `av_frame_clone()` 增加引用计数
2. `av_frame_unref()` 减少引用计数（不释放内存直到refcount=0）
3. `av_frame_free()` = `av_frame_unref()` + 释放AVFrame结构体本身
4. 传递AVFrame指针给其他模块时，必须先clone再unref原始帧

#### 问题16：H264 I帧超过1MB

**现象：** H264编码后的I帧（关键帧）可能达到2-3MB，超过安全传输阈值

**根因分析：**
- I帧包含完整图像信息，压缩率远低于P帧
- 高分辨率（如640x480）下的I帧可能超过1MB
- 服务端设计的单包处理上限为1MB

**解决方案：** 4KB分片传输
```cpp
// 发送端：分片
#define H264_FRAGMENT_SIZE 4096

void ckernel::sendH264Frame(QByteArray h264Data, int frameType)
{
    int totalFragments = (h264Data.size() + H264_FRAGMENT_SIZE - 1) / H264_FRAGMENT_SIZE;
    static int frameSeq = 0;

    for (int i = 0; i < totalFragments; i++) {
        int offset = i * H264_FRAGMENT_SIZE;
        int fragSize = qMin(H264_FRAGMENT_SIZE, h264Data.size() - offset);

        // 构造分片包
        QByteArray packet;
        STRU_VIDEO_FRAME_H264_HEADER header;
        header.m_userid = m_id;
        header.m_roomid = m_roomid;
        header.m_frameType = frameType;
        header.m_frameSeq = frameSeq;
        header.m_totalFragments = totalFragments;
        header.m_fragmentIndex = i;

        packet.append((char*)&header, sizeof(header));
        packet.append(h264Data.data() + offset, fragSize);

        // 通过视频连接发送
        m_pAVClient[2]->SendData(0, packet.data(), packet.size());
    }
    frameSeq++;
}
```

## 八、音视频同步模块开发

### 8.1 音频主时钟方案设计

参考ffplay的音视频同步方案，以音频为基准（主时钟），视频跟随音频节奏显示。

**设计原理：**
- 人耳对音频断续（卡顿）非常敏感，约1-2ms的断续就能察觉
- 人眼对视频帧延迟不敏感，约30-50ms的偏差不可察觉
- 因此以音频为主时钟，视频调整显示时间来匹配音频

### 8.2 核心数据结构

```cpp
// AVSyncManager.h
struct SyncContext {
    double audioClock = 0.0;        // 音频时钟（秒）
    double videoClock = 0.0;        // 视频时钟（秒）
    double lastAudioPts = 0.0;      // 最近音频PTS
    double lastVideoPts = 0.0;      // 最近视频PTS
    std::atomic<bool> audioClockValid{false};  // 音频时钟是否有效
    std::atomic<bool> videoClockValid{false};  // 视频时钟是否有效
};

class AVSyncManager {
private:
    static AVSyncManager s_instance;                    // 单例
    std::map<int, SyncContext> m_syncContexts;          // 每用户独立时钟
    std::mutex m_mutex;                                 // 线程安全

    double m_localAudioClock = 0.0;                     // 本地音频时钟
    double m_localVideoClock = 0.0;                     // 本地视频时钟
    std::mutex m_localMutex;

    static constexpr double SYNC_THRESHOLD = 0.01;      // 同步阈值10ms
    static constexpr int MAX_WAIT_MS = 100;             // 最大等待100ms
    static constexpr double CLOCK_TIMEOUT = 5.0;        // 时钟超时5秒
};
```

### 8.3 同步算法实现

```cpp
// AVSyncManager.cpp

// 音频时钟更新（每次解码音频帧时调用）
void AVSyncManager::updateAudioClock(int userId, double pts)
{
    std::lock_guard<std::mutex> lck(m_mutex);
    auto& ctx = m_syncContexts[userId];
    ctx.audioClock = pts;
    ctx.lastAudioPts = getCurrentTimeUs() / 1000000.0;
    ctx.audioClockValid.store(true);
}

// 视频同步延迟计算
int AVSyncManager::computeSyncDelay(int userId)
{
    std::lock_guard<std::mutex> lck(m_mutex);
    auto it = m_syncContexts.find(userId);
    if (it == m_syncContexts.end()) return 0;

    SyncContext& ctx = it->second;

    // 音频时钟未就绪，直接显示视频
    if (!ctx.audioClockValid.load()) return 0;

    // 检查时钟超时
    double now = getCurrentTimeUs() / 1000000.0;
    if (now - ctx.lastAudioPts > CLOCK_TIMEOUT) {
        ctx.audioClockValid.store(false);  // 时钟失效
        return 0;
    }

    // 计算音视频差值
    double diff = ctx.audioClock - ctx.videoClock;

    if (diff > SYNC_THRESHOLD) {
        // 视频超前音频：等待
        int waitMs = (int)(diff * 1000);
        return qMin(waitMs, MAX_WAIT_MS);  // 最大等待100ms
    } else if (diff < -SYNC_THRESHOLD) {
        // 视频落后音频：立即显示（丢帧追赶）
        return -1;
    }

    // 同步正常
    return 0;
}

// 视频同步显示（ckernel中调用）
void ckernel::synchronizeVideo(int userId, QImage& img)
{
    int delay = AVSyncManager::getInstance().computeSyncDelay(userId);
    if (delay > 0) {
        QThread::msleep(delay);  // 等待音频追赶
    }
    // 立即显示（delay==0或delay==-1）
    m_pRoomdialog->slot_refreshUser(userId, img);
}
```

### 8.4 问题与解决方案

#### 问题19：新用户加入房间时同步状态异常

**现象：** 新成员加入后，收到的第一帧视频等待时间过长（可能等待数秒）

**解决方案：** `audioClockValid` 原子标志位，音频时钟未就绪时直接显示视频帧不等待

#### 问题20：长时间通话后音视频逐渐失步

**现象：** 通话30分钟后，音视频偏差逐渐增大到200-500ms

**根因分析：** 音频和视频的系统时钟存在微小漂移（约1-10ppm），长时间累积导致偏差

**解决方案：** SyncContext 5秒超时机制
```cpp
// 检查时钟是否超时（5秒未更新则失效）
double now = getCurrentTimeUs() / 1000000.0;
if (now - ctx.lastAudioPts > CLOCK_TIMEOUT) {
    ctx.audioClockValid.store(false);  // 时钟失效，视频直接显示
    // 下一次音频帧到达时重新建立同步
}
```

#### 问题22：config.ini IP地址错误

**现象：** 客户端连接旧IP 192.0.2.129 失败，但代码中已改为192.0.2.130

**根因分析：** `ckernel::initConfig()` 先设置默认值，再检查config.ini是否存在。config.ini优先级高于代码默认值。

**解决方案：** 修改所有config.ini文件
```ini
# config.ini
ip=192.0.2.130
port=8000
```

## 十、优化迭代

### 10.1 性能优化汇总

| 优化项 | 优化前 | 优化后 | 技术手段 | 提升幅度 |
|--------|--------|--------|----------|----------|
| 视频编码 | JPEG软编 ~300KB/帧 | H264硬件编码 ~120KB/帧 | NVENC/QSV/libx264回退链 | 带宽-60%，延迟-80% |
| 音频编码 | Speex 8kHz ~76字节/帧 | Opus 48kHz ~60-120字节/帧 | Opus VOIP+DTX+FEC | 音质从电话级→宽带级 |
| 音频采集 | QTimer轮询 ±5ms | SDL回调 ±0.5ms | SDL_OpenAudioDevice回调驱动 | 延迟精度提升10倍 |
| 视频渲染 | QPainter CPU软渲染 | OpenGL GPU渲染 | VAO/VBO+GLSL三纹理YUV420P | CPU占用-50% |
| 视频发送 | 主线程直接TCP send | 子线程发送+丢帧策略 | SendVideoWorker+300ms丢帧 | UI不再卡顿 |
| 协议分发 | if-else链 O(n) | 函数指针映射表 O(1) | m_netPackMap[100] | 分发延迟降低 |
| 解码帧传递 | memcpy拷贝 | av_frame_clone零拷贝 | 引用计数机制 | 内存带宽降低 |

### 10.2 内存管理优化

**核心原则：** AVFrame使用引用计数零拷贝传递，避免大块内存复制

```
优化前：decode → memcpy → 传递 → memcpy → 渲染 → free
优化后：decode → clone → 传递 → 渲染 → free（引用计数自动管理）
```
