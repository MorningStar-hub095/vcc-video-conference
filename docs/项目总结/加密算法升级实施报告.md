| 项目 | 内容 |
|------|------|
| 升级目标 | 服务端密码存储从「明文 MD5 哈希」升级为「bcrypt 自适应哈希」 |
| 实施日期 | 2026-08-16 |

## 三、核心实现要点

### 3.1 bcrypt 封装模块

- 使用 Linux `crypt_r()`（线程安全版本），链接 `-lcrypt`。
- 成本因子 `BCRYPT_COST = 12`（2^12 = 4096 轮迭代）。

### 3.2 相对 P0 文档的两处安全性增强

| 项目 | P0 原方案 | 本方案 | 增强点 |
|------|----------|--------|--------|
| 盐值生成 | `rand()` + `time()` | `/dev/urandom` 读 22 字节，`byte % 64` 映射 | 消除可预测盐值；256 = 4×64 无取模偏置 |
| 哈希比较 | `strcmp()` | 异或累加常量时间比较 | 消除时序侧信道 |

### 3.3 注册流程（RegisterRq）

客户端 MD5 哈希 → `bcrypt_hash()` → `bcrypt(MD5值 + 随机盐)` → 入库。
`bcrypt_hash` 失败时拒绝入库并返回失败码，不降级为明文/空密码。

### 3.4 登录流程（LoginRq）与旧密码自动迁移

- 库中密码以 `$2` 开头（新格式）→ `bcrypt_verify()` 验证。
- 否则（旧 MD5 格式）→ `strcmp` 验证，成功后自动 `bcrypt_hash` 并 `update` 回库。
- MD5 哈希为 32 位十六进制（`0-9a-f`），永不以 `$2` 开头，格式判断无歧义。

### 4.2 功能/性能/安全测试（待 Linux 环境执行）

> **限制说明：** 当前开发环境为 Windows，服务端依赖 Linux `crypt.h`/`libcrypt`/`epoll`/`mysqlclient`，无法在本机编译与运行。以下测试需在 Linux 目标机执行。

**功能测试步骤：**

1. 部署前确认列宽：`ALTER TABLE t_user MODIFY password VARCHAR(64) NOT NULL;`（bcrypt 哈希 60 字符）。
2. 编译：`cd server/PlayerHallServer && qmake && make`。
3. 注册新用户 → 查库确认 `password` 为 60 字符、以 `$2b$12$` 开头。
4. 新用户登录 → 成功。
5. 旧 MD5 用户登录 → 成功，且登录后 `password` 自动变为 `$2b$12$`。
6. 错误密码 → 返回 `password_error`。
7. 同一密码注册两次 → 两次哈希不同（验证随机盐）。

**性能测试步骤：**

```bash
# 独立验证 bcrypt 单次耗时（可选，快速基准）
cat > /tmp/bench.cpp <<'EOF'
#include "bcrypt_wrapper.h"
#include <chrono>
#include <iostream>
int main(){
    auto t0=std::chrono::steady_clock::now();
    std::string h=bcrypt_hash("0123456789abcdef0123456789abcdef");
    auto t1=std::chrono::steady_clock::now();
    bool ok=bcrypt_verify("0123456789abcdef0123456789abcdef",h);
    auto t2=std::chrono::steady_clock::now();
    std::cout<<"hash_ms="<<std::chrono::duration_cast<std::chrono::milliseconds>(t1-t0).count()
             <<" verify_ms="<<std::chrono::duration_cast<std::chrono::milliseconds>(t2-t1).count()
             <<" verify_ok="<<ok<<"\n";
}
EOF
g++ -std=c++11 -I include /tmp/bench.cpp src/bcrypt_wrapper.cpp -lcrypt -o /tmp/bench && /tmp/bench
```

通过标准：单次 hash/verify 约 100~300ms（cost=12 预期区间）。

**安全扫描步骤：**

1. 抽查两次 `bcrypt_hash` 盐值不同。
2. 代码审查确认无 `strcmp` 直接比较 bcrypt 哈希结果（比较走 `constant_time_equals`）。
3. 用 hashcat 对泄露哈希做 1 分钟爆破 → 预期无法破解。

## 五、执行中发现的偏差

| 偏差 | 说明 | 处理 |
|------|------|------|
| 服务端存在**两份完全相同的并行副本**（根 `PlayerHallServer\` 与嵌套 `PlayerHallServer\PlayerHallServer\`） | 原计划仅改嵌套版（误判根版为废弃副本），实际根版含同等新逻辑且各有 `.pro` 构建入口 | 已将改动同步应用到两份副本，避免遗漏导致一处仍存明文 MD5 |

## 六、遗留风险与建议

| 风险/建议 | 说明 |
|----------|------|
| SQL 注入（既有缺陷） | `sprintf` 拼接 SQL 仍存在注入风险，属既有问题，不在本次范围，建议后续参数化 |
| 客户端仍用 MD5 + 硬编码盐 | 协议不变是本期约束；建议 P1 阶段去除客户端 MD5，直接发送明文密码走 TLS |
| 双副本维护成本 | 两份服务端副本需长期保持一致，建议明确唯一构建入口并删除冗余副本 |
| 算法升级空间 | 如需更强抗 ASIC 能力，可评估 scrypt/Argon2id（需新增依赖） |

## 七、结论

已完成服务端密码哈希 MD5→bcrypt 的代码升级与双副本同步，安全性显著提升（抗暴力破解成本提升约 10^6 倍，消除固定盐彩虹表攻击与常量时间比较侧信道）。功能/性能/安全实测需在 Linux 环境按第四节步骤执行，客户端零改动、旧密码自动迁移保证了兼容性。
