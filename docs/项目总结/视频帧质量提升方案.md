## 一、文档概述

### 1.1 方案背景

VCC视频会议 音视频会议系统早期采用 320×240(QVGA) 分辨率，远低于行业最低标准。经过 SD(640×480) 阶段验证后，H264 编码路径稳定性已确认。本方案将视频质量从 SD 级别全面升级到 **HD(1280×720) 级别**，桌面共享升级到 **FHD(1920×1080)**，所有技术指标与高清 HD 级别目标完全一致。

### 1.2 方案原则

| 原则 | 说明 |
|------|------|
| **HD为标准** | 1280×720 摄像头、1920×1080 桌面共享为正文主线和默认配置 |
| **SD为回退** | 640×480 摄像头、1280×720 桌面共享作为弱网/低配场景的自动回退方案 |
| **代码保留** | 所有原有代码通过注释保留，不删除，修改处均有 `[HD升级]` 标记 |
| **渐进式升级** | 从 SD→HD 平滑过渡，保持编码路径稳定性 |

### 1.3 版本演进

| 版本 | 日期 | 内容 |
|------|------|------|
| v1.0 | 2026-07-27 | SD级别升级方案（320×240 → 640×480） |
| v1.1 | 2026-07-29 | 补充H264编码路径稳定性验证结论 |
| **v2.0** | **2026-07-31** | **HD级别全面升级（640×480 → 1280×720，桌面共享 → 1920×1080）** |

## 四、SD回退方案

### 4.1 回退触发条件

| 触发条件 | 检测方式 | 回退动作 |
|----------|----------|----------|
| **网络带宽不足** | 发送队列深度 > 阈值 | 分辨率降至640×480，码率降至1.2Mbps |
| **编码延迟超标** | 单帧编码 > 25ms | preset降至veryfast |
| **摄像头不支持720p** | 启动时查询设备能力 | 分辨率降至640×480 |
| **CPU占用过高** | CPU占用 > 80% | 帧率降至15fps |
| **丢包率过高** | TCP重传率 > 10% | 分辨率降至640×480 |

### 4.3 回退实现方式

当前阶段SD回退参数以代码注释形式保留，需要手动切换。未来可实现自适应码率（ABR）机制自动切换：

## 五、技术选型

### 5.1 方案A：直接提升采集分辨率（已采用）

**原理：** 直接将摄像头采集分辨率从640×480提升到1280×720，同时调整编码参数。

| 维度 | 评估 |
|------|------|
| **实现复杂度** | 低（修改参数值+注释保留原值） |
| **画质提升效果** | 极高（像素数×3） |
| **CPU/GPU开销** | 中等增加（faster preset + 更高分辨率） |
| **带宽需求** | 显著增加（×2.5） |
| **兼容性** | 需要服务端配合（H264分片增大） |
| **风险** | 低（SD阶段已验证编码路径稳定性） |
| **状态** | ✅ 已实施 |

### 5.2 方案B：软件超分辨率增强

**原理：** 保持低分辨率采集，通过AI超分辨率算法将图像上采样到目标分辨率。

| 维度 | 评估 |
|------|------|
| **实现复杂度** | 高（集成AI模型、GPU推理） |
| **画质提升效果** | 中等（无法恢复真实细节） |
| **CPU/GPU开销** | 极高（实时推理需GPU） |
| **带宽需求** | 不变（编码分辨率不变） |
| **兼容性** | 需要NVIDIA GPU |
| **风险** | 高（延迟增加、模型兼容性） |
| **状态** | 长期规划（见第十章） |

### 5.3 方案对比总结

| 评估维度 | 方案A(直接提升) | 方案B(超分辨率) |
|----------|----------------|----------------|
| **画质提升** | ★★★★★ | ★★★ |
| **实现难度** | ★☆☆☆☆ | ★★★★☆ |
| **延迟影响** | ★☆☆☆☆ | ★★★★☆ |
| **带宽需求** | 增加2.5倍 | 不变 |
| **CPU/GPU开销** | 中等增加 | 极高 |
| **兼容性** | 全平台 | 仅GPU平台 |
| **推荐度** | **已采用** | 长期规划 |

**最终选择：方案A（直接提升），HD级别已全面实施。方案B作为长期规划保留。**

## 十、超分辨率增强（长期规划）

### 10.1 目标

在弱网或低分辨率摄像头场景下，通过AI算法提升画质，作为HD直接提升方案的补充。

### 10.2 技术路线

| 步骤 | 内容 | 技术方案 |
|------|------|----------|
| 4.1 | 集成OpenCV DNN模块 | 使用ESPCN模型进行4×上采样 |
| 4.2 | 模型选择与优化 | Real-ESRGAN lite版（移动端优化） |
| 4.3 | GPU推理集成 | ONNX Runtime / TensorRT |
| 4.4 | 自适应策略 | 根据网络状况自动切换HD直接提升+超分辨率增强 |

### 10.3 可选算法

| 算法 | 上采样倍数 | 推理速度(640→1280) | GPU需求 | 画质(PSNR) |
|------|-----------|---------------------|---------|-----------|
| Real-ESRGAN | 2× | ~8ms(GPU) | 必需 | ~30dB |
| ESRGAN | 2× | ~15ms(GPU) | 必需 | ~29dB |
| OpenCV DNN (ESPCN) | 2× | ~3ms(GPU) | 推荐 | ~26dB |
| bicubic上采样 | 任意 | <1ms(CPU) | 无需 | ~24dB |

### 10.4 资源需求

| 资源 | 需求 |
|------|------|
| 开发工时 | 2-4周 |
| GPU依赖 | NVIDIA CUDA / Intel OpenVINO |
| 模型大小 | ESPCN: ~100KB / Real-ESRGAN: ~65MB |
| 额外延迟 | 3-15ms/帧(GPU) / 30-100ms/帧(CPU) |

### 10.5 适用场景

- 弱网环境：SD采集 + 超分辨率 → 接近HD画质，带宽不变
- 低分辨率摄像头：640×480采集 + 2×超分 → 1280×720显示
- 桌面共享增强：1920×1080 + 超分 → 4K显示
