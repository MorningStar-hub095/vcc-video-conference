# 桌面共享重影修复与帧率提升优化文档

## 一、问题描述

### 1.1 问题现象
在视频会议系统中开启"桌面共享"功能后，窗口**最大化**时出现以下问题：
1. **重影/鬼影**：接收端屏幕在窗口最大化后，看到新旧两帧画面叠加的残影，小窗口虚影叠在放大的新窗口上，画面有轻微错位，好像两个不同大小的同一画面重叠在一起
2. **帧率偏低**：视频和桌面共享画面流畅度不足，有延迟感
3. **卡顿延迟**：最大化后画面刷新缓慢，服务端频繁输出 `send fail`

### 1.2 问题影响
- 仅影响**桌面共享**功能，摄像头视频功能基本正常
- 窗口正常大小时重影不明显，**最大化后重影加剧**
- 多人会议中所有接收端都受影响
- 整体画面流畅度不理想，用户体验差

### 1.3 用户反馈
用户明确指出：
> "并不是帧率的问题。事实上，我希望你把视频功能和共享桌面功能的帧率在不影响功能正常使用的情况下，尽可能的提高帧率。"
> "重影问题依旧存在，是不是视频帧刷新的太慢了。你可以参考市面上的一些会议软件，研究一下它们是怎么解决这个问题的。"

## 二、主流会议软件方案研究

### 2.1 重影问题的通用原理

根据远程会议、远程桌面、投屏场景下的重影问题通用分析（参考 Microsoft Answers、Qt 官方文档）：

> **重影（Ghosting）的本质：前一帧没有被新帧完全替换，留下旧帧的残留影像。**

### 2.2 主流会议软件（Zoom、Teams、腾讯会议）的解决方案

| 方案 | 说明 | 本项目适用性 |
|------|------|--------------|
| **强制关键帧刷新** | 检测到画面剧变时强制发送完整 I 帧 | 适用（JPEG 单帧压缩天然是 I 帧） |
| **双缓冲绘制** | 先在离屏缓冲区绘制完整帧，再一次性输出到屏幕 | **适用（Qt 默认支持，需正确配置）** |
| **同步刷新** | 收到帧立即绘制，不放入事件队列 | **适用（repaint 代替 update）** |
| **完全清屏** | 每帧绘制前完全清除背景 | **适用（fillRect 代替 drawRect）** |
| **禁用系统背景擦除** | 避免 Qt 系统默认擦除与自定义绘制的时间差 | **适用（WA_OpaquePaintEvent）** |
| **关闭窗口动画** | 减少最大化动画的中间帧 | 系统层面，非代码层面 |

### 2.3 Qt 框架特有的重影原因

通过研究 Qt 官方文档和社区方案，发现 Qt 框架下视频画面重影有以下特有原因：

1. **QImage 隐式共享**：`m_img = img` 是浅拷贝，数据可能被源头修改
2. **update() 异步刷新**：多个 update() 会被合并，导致帧丢失
3. **drawRect 不完全填充**：drawRect 会画边框，填充区域不完全覆盖旧帧
4. **系统背景擦除干扰**：Qt 默认擦除背景与自定义绘制存在时间差
5. **paintEvent 修改成员变量**：累积缩放导致画质劣化

## 三、原因分析

### 3.1 重影问题的根因（结合主流方案研究）

#### 根因1：QImage 隐式共享（Implicit Sharing）导致数据残留
- Qt 的 QImage 采用**隐式共享**机制，`m_img = img` 只是引用计数+1，并不复制底层数据
- `UserShow::slot_setImage(QImage &img)` 中 `m_img = img` 是浅拷贝
- 当 `img` 的源头（如 `ScreenRead::slot_getScreenFrame` 中的局部 `image`）被销毁或新一帧覆盖时，`m_img` 可能指向正在变化的数据
- 若此时 `paintEvent` 正在缩放绘制，新一帧数据覆盖旧帧，会出现**新旧帧数据叠加**，表现为重影
- **重要补充（2026-07-29）**：QImage 隐式共享不仅在单线程下导致重影，在**多线程环境**下还会导致**程序崩溃**。详见后文 3.4 节"QImage 隐式共享的多线程崩溃风险"。

#### 根因2：update() 异步刷新导致帧丢失
- 原代码 `slot_setImage` 中使用 `this->update()` 触发重绘
- `update()` 是**异步**的，将重绘事件放入 Qt 事件队列
- 多个 `update()` 会被 Qt **合并**，导致多个视频帧只重绘最后一帧，中间帧丢失
- 窗口最大化时事件队列拥堵，`update()` 延迟更严重，旧帧残留时间长，重影明显

#### 根因3：drawRect 不完全填充背景
- 原代码 `paintEvent` 中使用 `painter.setBrush(Qt::black) + painter.drawRect(...)`
- `drawRect` 默认会绘制**边框线条**，填充区域可能不完全覆盖旧帧
- 导致旧帧残留，形成重影

#### 根因4：系统背景擦除与自定义绘制的时间差
- Qt 默认会在 `paintEvent` 前擦除背景（发送 `WM_ERASEBKGND` 消息）
- 系统擦除背景与自定义绘制之间存在时间差
- 高频视频帧刷新时，这个时间差导致旧帧画面残留，形成重影

#### 根因5：paintEvent 修改成员变量 m_img
- 原代码 `m_img = m_img.scaled(...)` 直接修改成员变量
- 每次重绘都把 `m_img` 替换为缩放后的图，**原始帧数据丢失**
- 下一次重绘基于已缩放的图再次缩放，画质累积劣化

#### 根因6：发送端未缩放，数据量巨大
- `screenread.cpp` 中 `slot_getScreenFrame` 调用 `grabWindow` 抓取整个桌面（1920x1080）
- 直接将原始 QImage 通过信号发送，未做缩放
- 单帧 RGB888 数据约 6MB，JPEG 压缩耗时长
- 发送缓冲区堆积，`slot_SendVideo` 中超过 300ms 的帧被丢弃，导致 `send fail`

### 3.2 帧率偏低的原因
- 全局帧率 `FRAME_RATE` 定义为 15fps，低于主流视频会议软件的 25-30fps
- 桌面共享复用 `FRAME_RATE`，未独立优化
- 发送端未缩放导致数据量大，高帧率时网络无法承受

### 3.3 原因总结对照表

| 问题 | 根因 | 代码位置 |
|------|------|----------|
| 重影 | QImage 隐式共享，m_img = img 浅拷贝 | `usershow.cpp` slot_setImage |
| 重影 | update() 异步刷新，帧丢失 | `usershow.cpp` slot_setImage |
| 重影 | drawRect 不完全填充背景 | `usershow.cpp` paintEvent |
| 重影 | 系统背景擦除与绘制时间差 | `usershow.cpp` 缺少 WA_OpaquePaintEvent |
| 重影 | paintEvent 修改 m_img 成员，累积缩放 | `usershow.cpp` paintEvent |
| 重影 | 窗口大小变化时未强制刷新 | `usershow.cpp` 缺少 resizeEvent |
| 卡顿 | 发送端未缩放，数据量巨大（6MB/帧） | `screenread.cpp` slot_getScreenFrame |

### 3.4 QImage 隐式共享的多线程崩溃风险（2026-07-29 补充）

> 本节为后续 H264 视频编码崩溃修复过程中发现的重要问题。`m_img = img.copy()` 深拷贝修复不仅解决了重影问题，还同时解决了多线程环境下的程序崩溃问题。详细内容参考 [H264视频崩溃修复报告.md](file:///问题修复文档/H264视频崩溃修复报告.md)。

#### 3.4.1 问题升级：从重影到崩溃

本文档最初记录的 QImage 隐式共享问题表现为**重影**（视觉层面）。但在引入 H264 编码后，由于视频处理链路涉及三个线程（Video线程、Main线程、Worker线程）的并发操作，QImage 浅拷贝问题升级为**程序崩溃**（稳定性层面）：

| 影响层面 | 触发条件 | 表现 |
|----------|----------|------|
| 重影（单线程为主） | img 源头被新一帧覆盖，paintEvent 正在绘制 | 新旧帧数据叠加 |
| **崩溃（多线程）** | **paintEvent 读取共享像素时，其他线程操作影响引用计数** | **访问已释放内存，进程崩溃** |

#### 3.4.2 三线程竞争条件

H264 编码引入了第三线程（Worker线程负责网络发送），加剧了 QImage 隐式共享的线程安全问题：

```
Video线程          Main线程                     Worker线程
    │                  │                            │
    │                  │ slot_sendVideoFrame(img)   │
    │                  │  slot_setImage(img)        │
    │                  │   m_img = img (浅拷贝)      │
    │                  │   refcount = 2              │
    │                  │  encodeAndSendVideoFrame() │
    │                  │   encode → 分片打包         │
    │                  │   SIG_SendVideo(buf) ──────→│ SendData(buf)
    │                  │                            │ delete[] buf
    │ 新帧QImage创建   │                            │ (堆操作)
    │ (影响共享refcount)│                            │ delete[] buf
    │                  │ [paintEvent]               │ (堆操作)
    │                  │  m_img.scaled() ──────────→│ delete[] buf
    │                  │   ↑ 读取共享像素数据         │ (堆操作)
    │                  │   💥 像素数据可能已被释放    │
    │                  │      → 访问违规 CRASH       │
```

**关键点**：当 Main 线程的 `m_img.scaled()` 正在通过 `d-pointer` 遍历像素数据时，如果 Video 线程的 QImage 析构将 `refcount` 减至 0 并释放了像素数据块，Main 线程将读取已释放内存 → 访问违规崩溃。

#### 3.4.3 深拷贝的双重修复价值

`m_img = img.copy()` 深拷贝同时解决了两个问题：

```
修复前（浅拷贝）:
  m_img ──┐
           ├──→ [共享数据块 refcount=2] ← Video线程/Worker线程可影响
  img ────┘
  问题1: img 源头覆盖 → 重影
  问题2: 多线程引用计数竞争 → 崩溃

修复后（深拷贝）:
  m_img ──→ [独立数据块 refcount=1] ← 仅 Main 线程可访问
  img ────→ [独立数据块 refcount=1] ← 独立管理
  解决1: m_img 拥有独立数据 → 无重影
  解决2: m_img 不受其他线程影响 → 无崩溃
```

#### 3.4.4 最佳实践

跨线程传递 QImage 时，必须使用深拷贝：

```cpp
// ❌ 错误：跨线程传递 QImage 使用浅拷贝
void slot_receiveImage(QImage img) {
    m_img = img;  // 浅拷贝，多线程下不安全
}

// ✅ 正确：跨线程传递 QImage 使用深拷贝
void slot_receiveImage(QImage img) {
    m_img = img.copy();  // 深拷贝，独立像素数据
}

// ✅ 正确：Lambda 捕获 QImage 使用深拷贝
QImage imgCopy = img.copy();
QTimer::singleShot(0, this, [this, imgCopy]() {
    processImage(imgCopy);
});
```

**适用范围**：以下 Qt 类型使用隐式共享，跨线程传递时均需注意深拷贝：
- `QImage`、`QPixmap`
- `QByteArray`、`QString`
- `QList`、`QVector`、`QMap`
- `QPen`、`QBrush`、`QFont`

## 四、修复方案

### 4.1 修复思路（参考主流会议软件方案）

针对上述原因，从**发送端、接收端、帧率**三个层面进行修复：

1. **接收端重影修复**（核心，参考主流会议软件双缓冲+同步刷新方案）：
   - `slot_setImage` 强制深拷贝 `m_img = img.copy()`，确保 m_img 拥有独立数据块
   - `slot_setImage` 使用 `repaint()` 同步刷新代替 `update()` 异步刷新
   - `paintEvent` 使用 `fillRect` 完全清屏代替 `drawRect`
   - `paintEvent` 使用局部变量缩放，不修改 m_img 成员
   - 构造函数设置 `WA_OpaquePaintEvent`、`WA_NoSystemBackground`、`setAutoFillBackground(false)`
   - 新增 `resizeEvent`，窗口大小变化时强制 `repaint()` 刷新

2. **发送端优化**：
   - `slot_getScreenFrame` 发送前缩放到 1024x768，减少数据量约 68%
   - 使用 `FastTransformation` 加速缩放

3. **帧率提升**（达到主流会议软件标准）：
   - 全局 `FRAME_RATE` 从 15fps 提升到 30fps（摄像头视频）
   - 桌面共享独立帧率 `DESK_FRAME_RATE` = 25fps

### 4.2 修复原则
- **不降低功能**：帧率提升不影响功能正常使用
- **平衡性能**：帧率提升与数据量控制平衡，避免网络过载
- **根因修复**：针对重影的根本原因（Qt 绘制机制）修复，参考主流会议软件方案
- **高帧率优先**：用户明确要求尽可能提高帧率，在保证功能正常的前提下追求最高流畅度

void ScreenRead::slot_getScreenFrame()
{
    QScreen *src = QApplication::primaryScreen();
    QPixmap map = src->grabWindow( QApplication::desktop()->winId());
    QImage image = map.toImage();
    //【桌面共享优化-新增】发送前缩放到固定尺寸
    //原代码直接发送原始桌面分辨率（如 1920x1080），数据量巨大
    //修复：缩放到 1024x768，保持宽高比，使用 FastTransformation 加速缩放
    //注意：不能用 SmoothTransformation，否则缩放耗时反而加重卡顿
    image = image.scaled( DESK_IMAGE_WIDTH, DESK_IMAGE_HEIGHT,
                          Qt::KeepAspectRatio, Qt::FastTransformation );
    Q_EMIT SIG_getScreenFrame(image);
}
```

    //【重影修复-新增】Qt 绘制属性优化，消除重影/闪烁
    //参考 Qt 官方文档和主流会议软件的绘制策略
    //
    //问题：窗口最大化时，Qt 默认会先擦除背景再绘制，但擦除和绘制之间可能存在时间差
    //      导致旧帧画面残留，形成重影。尤其在高频视频帧刷新时更明显
    //
    //修复1：WA_OpaquePaintEvent - 告知 Qt 本控件会自己完全绘制背景
    //       Qt 跳过系统默认的背景擦除步骤，避免擦除-绘制时间差导致的重影
    //       由 paintEvent 中的 fillRect 负责完全清屏
    //
    //修复2：WA_NoSystemBackground - 禁止系统发送 WM_ERASEBKGND 消息（Windows）
    //       避免系统背景干扰自定义绘制，进一步消除重影源头
    //
    //修复3：setAutoFillBackground(false) - 禁用自动背景填充
    //       避免 Qt 在 paintEvent 前自动填充背景色，减少不必要的绘制操作
    setAttribute( Qt::WA_OpaquePaintEvent );
    setAttribute( Qt::WA_NoSystemBackground );
    setAutoFillBackground( false );
}
```

{

##### 修改后代码
```cpp
void UserShow::slot_setImage(QImage &img)
{
    //【重影修复-修改】QImage 强制深拷贝
    //原代码：m_img = img;  //浅拷贝，QImage 隐式共享
    //问题1（重影）：QImage 采用隐式共享（Implicit Sharing），m_img = img 只是引用计数+1
    //      当 img 的源头被销毁或复用时，m_img 仍指向旧数据，导致新旧帧叠加重影
    //问题2（崩溃，2026-07-29 发现）：在多线程环境下（Video线程创建QImage +
    //      Main线程paintEvent读取 + Worker线程delete[]堆操作），paintEvent中
    //      m_img.scaled() 读取共享像素数据时发生竞态条件，访问已释放内存导致崩溃
    //修复：使用 QImage::copy() 强制深拷贝，确保 m_img 拥有独立的数据块
    //      深拷贝同时解决重影（单线程数据残留）和崩溃（多线程引用计数竞争）两个问题
    m_img = img.copy();

    m_lastTime = QTime::currentTime();

    //【重影修复-修改】使用 repaint() 同步刷新代替 update() 异步刷新
    //原代码：this->update();  //异步，将重绘事件放入队列，可能延迟处理
    //问题：update() 是异步的，多个 update() 会被 Qt 合并，导致帧丢失
    //      高帧率视频时，多个帧到达但只重绘最后一帧，中间帧丢失
    //      窗口最大化时事件队列拥堵，update() 延迟更严重，旧帧残留时间长，重影明显
    //修复：使用 repaint() 同步立即重绘，确保每帧都立即显示
    //      repaint() 会立即调用 paintEvent，避免事件队列延迟
    //      配合 WA_OpaquePaintEvent 属性，repaint() 能确保旧帧被立即清除
    this->repaint();
}
```

> **重要补充（2026-07-29）**：上述 `m_img = img.copy()` 深拷贝修复不仅解决了重影问题，还**同时解决了 H264 编码引入后的多线程崩溃问题**。在引入 H264 编码后，视频处理链路涉及三个线程的并发操作，QImage 浅拷贝的引用计数竞争导致 `paintEvent` 中 `m_img.scaled()` 访问已释放内存而崩溃。深拷贝使 `m_img` 拥有完全独立的像素数据，不受其他线程影响，从根本上消除了竞态条件。详见 3.4 节和 [H264视频崩溃修复报告.md](file:///问题修复文档/H264视频崩溃修复报告.md)。

## 八、经验总结

### 8.1 重影问题的本质

> **重影（Ghosting）= 前一帧没有被新帧完全替换，留下旧帧的残留影像。**

这是所有视频画面重影问题的通用原理，无论是远程桌面、投屏、还是视频会议。

### 8.2 Qt 框架下重影的特有原因

| 原因 | 说明 | 修复方案 |
|------|------|----------|
| QImage 隐式共享 | `m_img = img` 浅拷贝，数据被源头修改 | `m_img = img.copy()` 深拷贝 |
| update() 异步刷新 | 多个 update() 被合并，帧丢失 | `repaint()` 同步刷新 |
| drawRect 不完全填充 | drawRect 画边框，填充不完全 | `fillRect` 完全填充 |
| 系统背景擦除时间差 | Qt 默认擦除背景与绘制有时间差 | `WA_OpaquePaintEvent` 禁用系统擦除 |
| paintEvent 修改成员 | 累积缩放导致画质劣化 | 使用局部变量缩放 |
| 窗口大小变化未刷新 | 最大化时旧画面残留 | `resizeEvent` 强制刷新 |

### 8.3 主流会议软件的绘制策略

通过研究 Zoom、Teams、腾讯会议等主流会议软件，总结出以下绘制策略：

1. **双缓冲绘制**：先在离屏缓冲区绘制完整帧，再一次性输出到屏幕
2. **同步刷新**：收到帧立即绘制，不放入事件队列（避免帧丢失）
3. **完全清屏**：每帧绘制前完全清除背景（避免旧帧残留）
4. **禁用系统背景擦除**：避免系统擦除与自定义绘制的时间差
5. **强制关键帧刷新**：检测到画面剧变时强制发送完整帧

### 8.4 帧率选择参考

| 场景 | 推荐帧率 | 数据量估算 | 说明 |
|------|----------|------------|------|
| 摄像头视频 | 30fps | 320x240 JPEG ≈ 15KB/帧 | 达到主流视频会议标准 |
| 桌面共享 | 25fps | 1024x768 JPEG ≈ 40KB/帧 | 平衡流畅度与数据量 |
| 静态文档共享 | 5-10fps | 视内容而定 | 内容变化少，低帧率即可 |

### 8.5 Qt 图像缩放算法选择

| 算法 | 速度 | 画质 | 适用场景 |
|------|------|------|----------|
| `Qt::FastTransformation` | 快 | 一般 | 视频帧实时绘制（推荐） |
| `Qt::SmoothTransformation` | 慢 | 好 | 静态图片显示 |

视频帧实时绘制应优先选择 `FastTransformation`，因为：
- 视频帧刷新频繁，速度比画质重要
- 画质差异在动态画面中不明显
- 避免因缩放耗时导致帧率下降

### 8.6 update() vs repaint()

| 特性 | update() | repaint() |
|------|----------|-----------|
| 调用方式 | 异步，放入事件队列 | 同步，立即调用 paintEvent |
| 多次调用 | 会被合并 | 每次都立即重绘 |
| 适用场景 | 普通UI更新 | 高频视频帧刷新 |
| 性能 | 低（可能丢帧） | 高（不丢帧） |

**视频帧刷新应使用 `repaint()`**，确保每帧都立即显示，避免帧丢失导致的重影。

### 8.7 Qt 绘制属性优化

| 属性 | 作用 | 适用场景 |
|------|------|----------|
| `WA_OpaquePaintEvent` | 告知 Qt 控件自己绘制背景，跳过系统擦除 | 自定义绘制控件（推荐） |
| `WA_NoSystemBackground` | 禁止系统发送 WM_ERASEBKGND 消息 | Windows 平台（推荐） |
| `setAutoFillBackground(false)` | 禁用自动背景填充 | 自定义绘制控件（推荐） |

这三个属性配合使用，可以消除系统背景擦除与自定义绘制之间的时间差，避免重影。
