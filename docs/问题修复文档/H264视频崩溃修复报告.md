## 一、问题概述

### 1.1 问题表现

启用 H264 视频编码后，客户端程序在成功编码并发送**第一帧**视频数据后立即崩溃退出。崩溃无错误对话框、无异常日志，程序被操作系统强制终止。

典型崩溃日志时序：

### 1.2 影响范围

| 影响维度 | 说明 |
|----------|------|
| **功能影响** | H264 视频编码功能完全不可用，程序在第一帧后崩溃 |
| **用户体验** | 视频通话功能无法使用，程序意外退出 |
| **回退方案** | 仅能使用 JPEG 编码（画质差、带宽占用高约 5 倍、帧率低） |
| **触发条件** | 启动视频通话，H264 编码器成功初始化后编码第一帧 |

### 1.3 关键特征

- 崩溃**总是在第一帧编码和发送完成后**发生
- 崩溃前所有操作（编码、分片、网络发送、内存释放）均报告成功
- 崩溃无 Windows 异常对话框，进程被直接强制终止
- 崩溃后无核心转储文件生成

## 二、系统架构与线程模型

### 2.1 视频处理全链路架构

理解崩溃问题需要先了解系统的多线程架构和数据流：

```
┌─────────────────────────────────────────────────────────────────────┐
│                        WeChat 视频会议系统                           │
├─────────────┬──────────────────────┬────────────────────────────────┤
│  Video线程   │     Main线程(UI)      │       Worker线程(网络)          │
│ (VideoRead)  │    (ckernel/Qt)      │    (slot_SendVideo)           │
├─────────────┼──────────────────────┼────────────────────────────────┤
│             │                      │                                │
│  OpenCV采集  │   事件循环处理        │   网络数据发送                  │
│  BGR→RGB转换 │   paintEvent绘制     │   delete[] buf                │
│  QImage创建  │   H264编码调度       │                                │
│  信号发射    │   分片打包           │                                │
│             │                      │                                │
│  QTimer(23ms)│  QTimer::singleShot  │   TcpClient::SendData         │
│      ↓       │       ↓              │       ↑                        │
│  SIG_send    │  encodeAndSend       │   SIG_SendVideo               │
│  VideoFrame  │  VideoFrame          │   (QueuedConnection)          │
│  (Queued)──────→ slot_send          │                                │
│             │    VideoFrame         │                                │
│             │       │              │                                │
│             │    img.copy()──────────→ encode → 分片 ──→ SIG_SendVideo│
│             │    slot_setImage      │                                │
│             │    this->update()     │                                │
│             │       │              │                                │
│             │    paintEvent         │                                │
│             │    m_img.scaled()     │                                │
│             │    QPainter绘制       │                                │
└─────────────┴──────────────────────┴────────────────────────────────┘
```

### 2.2 三线程职责说明

| 线程 | 类 | 职责 | 关键操作 |
|------|-----|------|----------|
| **Video线程** | `VideoRead` | 摄像头采集、格式转换、信号发射 | `cap.read()` → `cvtColor()` → `QImage` → `SIG_sendVideoFrame` |
| **Main线程** | `ckernel` / `UserShow` | 事件循环、编码调度、UI绘制 | `slot_sendVideoFrame` → `encodeAndSendVideoFrame` → `paintEvent` |
| **Worker线程** | `ckernel::slot_SendVideo` | 网络发送、缓冲区释放 | `SendData()` → `delete[] buf` |

### 2.3 视频帧数据流（详细）

以下是单帧视频从采集到发送的完整数据流：

```
步骤1: Video线程 — 摄像头采集
  VideoRead::slot_getVideoFrame()
    ├── cap.read(frame)                    // OpenCV Mat (BGR格式)
    ├── cvtColor(frame, frame, BGR2RGB)    // 转为RGB
    ├── QImage image(frame.data, ...)      // ⚠️ 浅引用Mat数据
    ├── image = image.scaled(640, 480)     // 创建新QImage(独立数据)
    └── Q_EMIT SIG_sendVideoFrame(image)   // 排队到Main线程

步骤2: Main线程 — 接收与分发
  ckernel::slot_sendVideoFrame(QImage img)  // img是队列拷贝(浅拷贝)
    ├── slot_refreshVideo(m_id, img)        // 更新UI预览
    │     └── UserShow::slot_setImage(img)
    │           ├── m_img = img             // ⚠️ 浅拷贝(问题根源!)
    │           └── this->update()          // 触发paintEvent
    ├── QImage imgCopy = img.copy()         // 深拷贝用于编码
    └── QTimer::singleShot(0, [imgCopy]() {
            encodeAndSendVideoFrame(imgCopy)
        })

步骤3: Main线程 — H264编码
  ckernel::encodeAndSendVideoFrame(QImage img)
    ├── m_h264Encoder->encode(img)          // H264编码
    │     ├── img.copy()                    // 深拷贝
    │     ├── av_frame_make_writable()      // 确保帧可写
    │     ├── sws_scale()                   // RGB→YUV420P
    │     ├── avcodec_send_frame()          // 发送到编码器
    │     └── avcodec_receive_packet()      // 接收编码数据
    ├── 分片打包 (H264_FRAGMENT_SIZE=4096)
    └── Q_EMIT SIG_SendVideo(buf, nlen)     // 排队到Worker线程

步骤4: Worker线程 — 网络发送
  ckernel::slot_SendVideo(char* buf, int nlen)
    ├── m_pAVClient->SendData(0, buf, nlen) // TCP发送
    └── delete[] buf                        // 释放分片缓冲区

步骤5: Main线程 — UI绘制 (与步骤4并发!)
  UserShow::paintEvent()
    ├── m_img.scaled(...)                   // ⚠️ 读取像素数据(崩溃点!)
    ├── QPixmap::fromImage(m_img)
    └── painter.drawPixmap(...)
```

## 三、排查过程（分阶段详解）

### 3.1 阶段一：FFmpeg 帧缓冲区管理问题

#### 3.1.1 假设

`av_image_alloc` 手动分配的帧缓冲区绕过了 FFmpeg 的 `AVBufferRef` 引用计数机制。`avcodec_send_frame` 内部调用 `av_frame_ref` 时发现 `buf[]` 为空，只能浅拷贝 `data` 指针。这导致编码器内部帧与外部帧共享同一块缓冲区，下一次 `encode()` 调用覆盖缓冲区时，编码器仍在读取 → 堆腐蚀。

#### 3.1.2 验证方法

将 `av_image_alloc` 替换为标准的 `av_frame_get_buffer`，并添加 `av_frame_make_writable` 确保帧缓冲区可写：

```cpp
// 修改前（有问题）
int bufSize = av_image_get_buffer_size(AV_PIX_FMT_YUV420P, width, height, 1);
m_yuvBuffer = (uint8_t*)av_malloc(bufSize);
av_image_fill_arrays(m_frame->data, m_frame->linesize, m_yuvBuffer,
                     AV_PIX_FMT_YUV420P, width, height, 1);

// 修改后（标准方式）
m_frame->format = AV_PIX_FMT_YUV420P;
m_frame->width  = width;
m_frame->height = height;
int ret = av_frame_get_buffer(m_frame, 0);  // 为每个平面创建 AVBufferRef

// 每次 encode 前调用
int ret = av_frame_make_writable(m_frame);  // 引用计数>1时自动分配新缓冲区
```

#### 3.1.3 结果

日志显示 `av_frame_get_buffer` 成功（`buf[0]` 指针非空），编码和发送均成功，但**崩溃依旧**。

#### 3.1.4 结论

帧缓冲区管理问题是真实存在的（需要修复），但不是崩溃的根本原因。排除此假设。

---

### 3.2 阶段二：FFmpeg DLL ABI 兼容性问题

#### 3.2.1 假设

MSVC 编译的 FFmpeg DLL 与 MinGW 32-bit 存在 ABI 不兼容，导致 `avcodec_send_frame` / `avcodec_receive_packet` 内部堆腐蚀。

#### 3.2.2 验证步骤

**步骤 1：检查 FFmpeg DLL 的编译工具链**

使用 Dependency Walker 或 `objdump` 检查 DLL 依赖：

```
ffmpeg\bin\avcodec-58.dll
  └── 依赖: msvcrt.dll (非 msvcrXXX.dll)
  └── 结论: MinGW 编译的 Zeranoe 构建，非 MSVC 编译
```

**步骤 2：检查导入库格式**

发现项目使用 MSVC 格式的 `.lib` 导入库，应使用 MinGW 格式的 `.dll.a`：

```pro
# 修改前（MSVC 格式，与 MinGW 链接器不完全兼容）
LIBS += $$PWD/ffmpeg-4.2.2/lib/libavcodec.lib \
        $$PWD/ffmpeg-4.2.2/lib/libavutil.lib \
        $$PWD/ffmpeg-4.2.2/lib/libswscale.lib

# 修改后（MinGW 标准格式）
LIBS += $$PWD/ffmpeg-4.2.2/lib/libavcodec.dll.a \
        $$PWD/ffmpeg-4.2.2/lib/libavutil.dll.a \
        $$PWD/ffmpeg-4.2.2/lib/libswscale.dll.a
```

**步骤 3：添加堆完整性检查**

在 `H264Encoder::encode()` 中添加 `HeapValidate` 检查：

```cpp
#include <windows.h>

// 编码前检查
if (!HeapValidate(GetProcessHeap(), 0, NULL)) {
    qCritical() << "HEAP CORRUPTED before avcodec_send_frame!";
    return QByteArray();
}

// 编码后检查
if (!HeapValidate(GetProcessHeap(), 0, NULL)) {
    qCritical() << "HEAP CORRUPTED after encoding!";
    return QByteArray();
}
```

#### 3.2.3 结果

- 导入库已切换为 `.dll.a`
- `HeapValidate` **全部通过**，堆未腐蚀
- 崩溃依旧

#### 3.2.4 结论

FFmpeg DLL 是 MinGW 编译的，与 MinGW 代码兼容。`.lib` → `.dll.a` 的切换是必要的（防止潜在问题），但不是崩溃原因。排除此假设。

---

### 3.3 阶段三：手动 RGB→YUV 转换缺陷

#### 3.3.1 假设

手动 BT.601 RGB→YUV420P 转换代码可能存在缓冲区越界写入，腐蚀了相邻堆内存。

#### 3.3.2 验证方法

用 FFmpeg 的 `sws_scale` 替代手动转换（DLL 确认为 MinGW 编译，`.dll.a` 链接正确）：

```cpp
// 修改前（手动转换，可能越界）
for (int y = 0; y < m_height; y++) {
    for (int x = 0; x < m_width; x++) {
        uint8_t r = row[x * 3];
        // ... 手动计算 Y/U/V 分量
        yPlane[y * yStride + x] = yVal;
        if ((y & 1) == 0 && (x & 1) == 0) {
            uPlane[(y >> 1) * uStride + (x >> 1)] = uVal;
            vPlane[(y >> 1) * vStride + (x >> 1)] = vVal;
        }
    }
}

// 修改后（FFmpeg sws_scale，SIMD 优化、边界检查完善）
m_swsCtx = sws_getContext(width, height, AV_PIX_FMT_RGB24,
                          width, height, AV_PIX_FMT_YUV420P,
                          SWS_BILINEAR, nullptr, nullptr, nullptr);

const uint8_t *srcData[1] = { rgbImg.constBits() };
int srcLinesize[1] = { rgbImg.bytesPerLine() };
sws_scale(m_swsCtx, srcData, srcLinesize, 0, m_height,
          m_frame->data, m_frame->linesize);
```

#### 3.3.3 结果

`sws_scale` 正常工作，`HeapValidate` 仍通过。崩溃依旧。

#### 3.3.4 结论

手动转换无越界问题。`sws_scale` 替代是合理的（更可靠、更高效），但不是崩溃原因。排除此假设。

### 3.4 阶段四：精确定位崩溃位置

#### 3.4.1 假设

崩溃不在编码路径中，而在编码完成后的 Qt 事件循环处理中。

#### 3.4.2 验证方法 — 三重诊断插桩

**插桩 1：paintEvent 全链路日志**

在 `UserShow::paintEvent` 中添加分步日志：

```cpp
void UserShow::paintEvent(QPaintEvent *event)
{
    qDebug() << "[paintEvent] enter, m_img.size:" << m_img.size()
             << "widget:" << this->width() << "x" << this->height();
    // ...
    qDebug() << "[paintEvent] scaling image...";
    QImage scaledImg = m_img.scaled(...);
    qDebug() << "[paintEvent] scaled OK:" << scaledImg.size();
    // ...
    qDebug() << "[paintEvent] done";
}
```

**插桩 2：心跳定时器**

在 `ckernel` 构造函数中添加 500ms 心跳定时器：

```cpp
QTimer *heartbeat = new QTimer(this);
heartbeat->setInterval(500);
connect(heartbeat, &QTimer::timeout, []() {
    qDebug() << "[heartbeat] main thread alive";
});
heartbeat->start();
```

**插桩 3：slot_SendVideo 的 delete[] 前后日志**

```cpp
qDebug() << "[slot_SendVideo] before delete[], buf=" << (void*)buf;
delete[] buf;
qDebug() << "[slot_SendVideo] after delete[], packType=" << packType;
```

#### 3.4.3 关键发现

诊断日志输出显示：

```
[heartbeat] main thread alive                    ← 主线程正常运行
[heartbeat] main thread alive

slot_sendVideoFrame called, img size: 640 x 480  ← 第一帧到达
[paintEvent] enter, m_img.size: QSize(640, 480)  ← paintEvent 被调用
                                                   widget: 241 x 200
[slot_SendVideo] before delete[], buf= 0xb3abc80 ← Worker线程并发执行
[slot_SendVideo] after delete[], packType= 10017
[paintEvent] scaling image...                     ← Main线程进入 scaled()
[slot_SendVideo] before delete[], buf= 0xb3accb0 ← Worker线程继续
[slot_SendVideo] after delete[], packType= 10017
（没有 "scaled OK" 日志）                          ← ⚠️ 崩溃在 scaled() 内部!

23:35:45: 程序异常结束。
```

#### 3.4.4 结论

**崩溃发生在 `QImage::scaled()` 调用中**，位于 `UserShow::paintEvent` 函数内。崩溃时：
- Main 线程正在执行 `m_img.scaled()` 读取像素数据
- Worker 线程正在并发执行 `delete[] buf` 堆操作
- Video 线程可能正在创建新的 QImage

## 四、根本原因分析

### 4.1 直接原因 — Qt 隐式共享的浅拷贝

`UserShow::slot_setImage` 中使用**浅拷贝**（Qt 隐式共享）赋值 `m_img`：

```cpp
// 原代码（有 Bug）
void UserShow::slot_setImage(QImage &img)
{
    m_img = img;  // ⚠️ 浅拷贝！m_img 与 img 共享同一块像素数据
    m_lastTime = QTime::currentTime();
    this->update();
}
```

### 4.2 Qt 隐式共享机制详解

Qt 的 `QImage` 使用**隐式共享**（Implicit Sharing / Copy-On-Write）机制来减少内存拷贝开销：

```
QImage A(frame.data, 640, 480, RGB888);  // A 持有数据
QImage B = A;                             // 浅拷贝: A 和 B 共享同一块像素数据
                                          //         引用计数 refcount = 2

// 此时内存状态:
// ┌──────────────┐
// │ QImage A     │──────┐
// │ d-pointer ───┤      │
// └──────────────┘      │
//                       ▼
// ┌──────────────┐    ┌─────────────────────┐
// │ QImage B     │──→│  共享数据块          │
// │ d-pointer ───┤    │  refcount: 2        │
// └──────────────┘    │  pixels: [RGB...]   │
//                      └─────────────────────┘

B.scaled(241, 200);  // 读取操作，不触发 detach
                      // 直接从共享数据读取像素

A.setPixel(0,0, ...); // 写入操作，触发 detach
                      // 1. 分配新数据块给 A
                      // 2. 复制像素数据
                      // 3. 原数据块 refcount-- (变为1)
                      // 4. B 仍指向原数据块
```

**问题**：在多线程环境下，`detach`（写时复制）过程中的引用计数操作**不是原子性的**。当一个线程读取共享数据（如 `scaled()` 读取像素），另一个线程的操作触发 `refcount` 变更时，存在竞态窗口。

### 4.3 崩溃时序分析

```
时间轴 ─────────────────────────────────────────────────────────────→

Video线程          Main线程                     Worker线程
    │                  │                            │
    │                  │ slot_sendVideoFrame(img)   │
    │                  │  slot_setImage(img)        │
    │                  │   m_img = img (浅拷贝)      │
    │                  │   refcount = 2              │
    │                  │   this->update()            │
    │                  │                            │
    │                  │  imgCopy = img.copy()       │
    │                  │  refcount = 3               │
    │                  │                            │
    │                  │  encodeAndSendVideoFrame()  │
    │                  │   encode → 分片打包         │
    │                  │   SIG_SendVideo(buf) ──────→│ SendData(buf)
    │                  │                            │ delete[] buf
    │                  │                            │ (堆操作)
    │                  │                            │
    │                  │  slot_sendVideoFrame 返回   │
    │                  │  img 析构                   │
    │                  │  refcount = 2               │
    │                  │                            │
    │ 新帧QImage创建   │                            │ delete[] buf
    │ (影响共享refcount)│                            │ (堆操作)
    │                  │                            │
    │                  │ [paintEvent]               │
    │                  │  m_img.scaled() ──────────→│ delete[] buf
    │                  │   ↑                        │ (堆操作)
    │                  │   │ 读取共享像素数据         │
    │                  │   │                        │
    │                  │   💥 像素数据可能已被释放    │
    │                  │      → 访问违规 CRASH       │
```

### 4.4 三方竞争条件详解

崩溃由三个线程的并发操作共同导致：

| 线程 | 操作 | 对共享数据的影响 |
|------|------|------------------|
| **Video线程** | 持续创建新 QImage 并通过 `SIG_sendVideoFrame` 发送 | 新 QImage 的创建和旧 QImage 的销毁会改变共享数据的引用计数 |
| **Main线程** | `paintEvent` 中 `m_img.scaled()` 读取像素数据 | `scaled()` 是只读操作，但需要通过 `d-pointer` 访问共享数据 |
| **Worker线程** | `delete[] buf` 执行堆操作 | 堆的 `free` 操作可能改变堆内存布局，加速共享数据块被回收 |

**竞态窗口**：当 Main 线程的 `m_img.scaled()` 正在通过 `d-pointer` 遍历像素数据时，如果 Video 线程的 QImage 析构将 `refcount` 减至 0 并释放了像素数据块，Main 线程将读取已释放内存 → 访问违规崩溃。

### 4.5 根因总结

```
根因: QImage 隐式共享在多线程环境下的非原子引用计数操作

触发条件:
  1. m_img = img (浅拷贝) 导致多个 QImage 共享像素数据
  2. paintEvent 的 scaled() 在 Main 线程读取共享数据
  3. Video 线程和 Worker 线程的并发操作改变了引用计数或堆状态

结果: scaled() 读取到已释放的像素数据 → 访问违规 → 进程崩溃
```

```cpp
void UserShow::slot_setImage(QImage &img)
{
    // [修复] 使用深拷贝而非浅拷贝，防止 paintEvent 中 scaled() 
    //       访问已释放的共享像素数据
    // 原Bug: m_img = img 是浅拷贝（Qt隐式共享），m_img 与 img 共享同一块像素数据。
    //        slot_sendVideoFrame 返回后 img 被销毁，引用计数减少。
    //        paintEvent 中 m_img.scaled() 读取像素数据时，如果引用计数管理出现
    //        并发问题（video线程可能正在创建新的QImage影响共享数据），会导致读取
    //        已释放内存 → 崩溃。
    // 修复: m_img = img.copy() 创建深拷贝，m_img 拥有完全独立的像素数据缓冲区，

        m_glWidget->hide();

    this->update();
}
```

#### 修复原理

```
修复前:  m_img ──┐
                 ├──→ [共享数据块 refcount=2] ← Video线程/Worker线程可影响
         img ────┘

修复后:  m_img ──→ [独立数据块 refcount=1] ← 仅 Main 线程可访问
         img ────→ [独立数据块 refcount=1] ← 独立管理
```

```cpp
void H264Encoder::freeResources()
{
    // 释放顺序: SwsContext → AVFrame → AVPacket → AVCodecContext
    // 注意: av_frame_free 会通过 AVBufferRef 自动释放缓冲区
    //       无需手动释放 m_yuvBuffer（已移除）

        sws_freeContext(m_swsCtx);
        m_swsCtx = nullptr;
    }
    if (m_frame) {
        av_frame_free(&m_frame);
    }
    if (m_pkt) {
        av_packet_free(&m_pkt);
    }
    if (m_codecCtx) {
        avcodec_free_context(&m_codecCtx);
    }
    m_frameIndex = 0;
}
```

#### 5.3.5 完整 encode 函数

```cpp
QByteArray H264Encoder::encode(const QImage &img)
{
    if (!m_codecCtx || !m_frame) {
        qWarning() << "H264Encoder::encode: encoder not ready";
        return QByteArray();
    }

    // 验证编码器上下文完整性
    if (m_codecCtx->width != m_width || m_codecCtx->height != m_height
        || m_codecCtx->pix_fmt != AV_PIX_FMT_YUV420P) {
        qWarning() << "H264Encoder::encode: codecCtx corrupted";
        return QByteArray();
    }

    // 深拷贝 QImage，防止 use-after-free
    QImage rgbImg;
    if (img.format() == QImage::Format_RGB888) {
        rgbImg = img.copy();
    } else {
        rgbImg = img.convertToFormat(QImage::Format_RGB888);
    }

    // 防御性尺寸校验
    if (rgbImg.width() != m_width || rgbImg.height() != m_height) {
        rgbImg = rgbImg.scaled(m_width, m_height, Qt::IgnoreAspectRatio);
    }
    if (rgbImg.isNull() || !rgbImg.constBits()) {
        qWarning() << "H264Encoder::encode: rgbImg is null";
        return QByteArray();
    }

    // 确保帧缓冲区可写
    int ret = av_frame_make_writable(m_frame);
    if (ret < 0) return QByteArray();

    // RGB → YUV420P 转换
    const uint8_t *srcData[1] = { rgbImg.constBits() };
    int srcLinesize[1] = { rgbImg.bytesPerLine() };
    sws_scale(m_swsCtx, srcData, srcLinesize, 0, m_height,
              m_frame->data, m_frame->linesize);

    // 设置 PTS 和关键帧标志
    m_frame->pts = m_frameIndex++;
    m_frame->pict_type = m_requestKeyFrame ? AV_PICTURE_TYPE_I 
                                           : AV_PICTURE_TYPE_NONE;
    m_requestKeyFrame = false;

    // 编码
    QByteArray result;
    ret = avcodec_send_frame(m_codecCtx, m_frame);
    if (ret < 0) return QByteArray();

    while (ret >= 0) {
        ret = avcodec_receive_packet(m_codecCtx, m_pkt);
        if (ret == AVERROR(EAGAIN) || ret == AVERROR_EOF) break;
        if (ret < 0) break;

        if (m_pkt->data && m_pkt->size > 0) {
            result.append(reinterpret_cast<const char*>(m_pkt->data), 
                         m_pkt->size);
        }
        av_packet_unref(m_pkt);
    }
    return result;
}
```

## 九、经验总结与最佳实践

### 9.1 Qt 隐式共享的线程安全陷阱

#### 陷阱说明

Qt 的隐式共享机制在**单线程**环境下是安全高效的，但在**多线程**环境下存在陷阱：

- `QImage` 的赋值 (`=`) 是浅拷贝，多个 QImage 对象共享同一块像素数据
- 引用计数管理在 `detach`（写时复制）时存在竞态窗口
- 当一个线程读取共享数据（如 `scaled()`），另一个线程修改引用计数时，可能导致数据被提前释放

#### 最佳实践

```cpp
// ❌ 错误：跨线程传递 QImage 使用浅拷贝
void slot_receiveImage(QImage img) {
    m_img = img;  // 浅拷贝，多线程下不安全
}

// ✅ 正确：跨线程传递 QImage 使用深拷贝
void slot_receiveImage(QImage img) {
    m_img = img.copy();  // 深拷贝，独立像素数据
}

// ✅ 正确：Lambda 捕获 QImage 使用深拷贝
QImage imgCopy = img.copy();
QTimer::singleShot(0, this, [this, imgCopy]() {
    processImage(imgCopy);
});
```

#### 适用范围

以下 Qt 类型使用隐式共享，跨线程传递时均需注意：
- `QImage`、`QPixmap`
- `QByteArray`、`QString`
- `QList`、`QVector`、`QMap`
- `QPen`、`QBrush`、`QFont`

### 9.2 崩溃诊断方法论

#### 有效的诊断手段（按优先级排列）

| 优先级 | 方法 | 适用场景 | 效果 |
|--------|------|----------|------|
| 1 | **逐步插桩法** | 崩溃位置未知 | 在关键路径添加日志，逐步缩小范围 |
| 2 | **堆完整性检查** | 怀疑堆腐蚀 | `HeapValidate` 确认堆状态 |
| 3 | **心跳监测法** | 怀疑线程死锁/崩溃 | 定时器监测线程存活状态 |
| 4 | **并发分析** | 多线程竞争条件 | 分析线程时序，识别竞态窗口 |

#### 无效的诊断方向（本次走过的弯路）

| 弯路 | 耗时 | 教训 |
|------|------|------|
| 误判 FFmpeg DLL 为 MSVC 编译 | ~1h | 应先检查 DLL 依赖（`msvcrt.dll` vs `msvcrXXX.dll`） |
| 过度关注 FFmpeg ABI 兼容性 | ~2h | `HeapValidate` 通过应排除堆腐蚀假设 |
| `signal(SIGSEGV)` + `setjmp/longjmp` | ~1h | 不跨 DLL 边界，且腐蚀 SEH 链导致更难诊断 |
| 手动 RGB→YUV 转换替代 sws_scale | ~1h | 应先确认 DLL 编译工具链再决定是否能用 |

### 9.3 FFmpeg 编码器使用最佳实践

#### 标准帧管理流程

```cpp
// 1. 初始化
m_frame = av_frame_alloc();
m_frame->format = AV_PIX_FMT_YUV420P;
m_frame->width  = width;
m_frame->height = height;
av_frame_get_buffer(m_frame, 0);  // 标准分配，创建 AVBufferRef

// 2. 每帧编码前
av_frame_make_writable(m_frame);  // 确保可写（引用计数 > 1 时自动分配新缓冲区）

// 3. 填充帧数据
sws_scale(m_swsCtx, ...);  // 使用 sws_scale 进行色彩空间转换

// 4. 编码
avcodec_send_frame(m_codecCtx, m_frame);
while (avcodec_receive_packet(m_codecCtx, m_pkt) >= 0) {
    // 处理编码数据
    av_packet_unref(m_pkt);
}

// 5. 释放
av_frame_free(&m_frame);      // 自动释放缓冲区（通过 AVBufferRef）
av_packet_free(&m_pkt);
avcodec_free_context(&m_codecCtx);
sws_freeContext(m_swsCtx);
```

#### 禁止事项

```cpp
// ❌ 禁止：使用 av_image_alloc 绕过 AVBufferRef
uint8_t *buffer = (uint8_t*)av_malloc(bufSize);
av_image_fill_arrays(m_frame->data, m_frame->linesize, buffer, ...);

// ❌ 禁止：不调用 av_frame_make_writable 直接写入 data[]
m_frame->data[0][0] = 255;  // 编码器可能仍持有引用

// ❌ 禁止：在同一对象上 close()+init() 重初始化
encoder->close();
encoder->init(...);  // FFmpeg 内部状态可能残留

// ✅ 正确：使用 delete+new 创建全新实例
delete encoder;
encoder = new H264Encoder(this);
encoder->init(...);
```

### 9.4 调试代码管理规范
